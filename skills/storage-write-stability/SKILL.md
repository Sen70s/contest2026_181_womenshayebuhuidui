# 存储写路径导致的稳定性问题：先隔离，再修

## 核心原则

**`[RSET]` / IWDT 复位是后果，不是原因。**
看门狗只是最后"收尸"的那个。先回答一个问题：**谁让心跳停了？**

在这块板上，答案经常是：**写/擦除 NOR 让系统阻塞了几十秒**。

## 故障画像

| 症状 | 先查 | 不要先查 |
|---|---|---|
| 周期性复位，日志最后是 `[RSET] WSR=00000020` | 复位前是否有 `NOR write` / `erase` 记录 | 把看门狗超时调大 |
| 黑屏 + 串口无崩溃栈 | UI 心跳线程最后一次打印的时间 | UI 代码、LVGL、显示驱动 |
| 只在"用了一会儿"之后复现 | 是否有周期性持久化（历史/健康/闹钟写盘） | 内存泄漏（除非有 memdump 证据） |
| 写 `/data` 返回失败但系统正常 | 是否已开只读（`-EROFS`） | 文件系统损坏 |

## 第一步：只读隔离法（最快的一次二分）

**目的**：不是修复，是**证伪**——如果关掉写路径后故障消失，根因就在写路径上。

```c
/* 本项目的做法：全局开关，让 MTD 的 write/erase 直接返回 -EROFS */
static bool g_nor_data_ro = true;

/* 驱动层拦截 */
if (g_nor_data_ro) {
    syslog(LOG_WARNING, "[%s] erase rejected (data read-only)\n", TAG);
    return -EROFS;
}
```

要求：

1. **负载保持一致**：同样的 TTS / LLM / 蓝牙压力，同样的时长
2. **跑够时间**：至少 8–10 分钟，覆盖"用一会儿才复现"的窗口
3. **记录证据**：串口日志留档，比对两个版本的 `up=` 时间

## 第二步：读证据，不要猜

对照实验要长这样（真实数据）：

| 版本 | `/data` 写入 | 结果 |
|---|---|---|
| v142 | 开 | TTS 结束后 `NOR write seq=960/1024/1088` → UI 心跳停 → 23 s 后 IWDT 复位 |
| v142b | 关（`-EROFS`） | **up=516 s，6×TTS + 3×LLM，零复位** |
| v132 | 开 | 6 分钟内 3 次 IWDT 复位 |

三条结论一次得到：
- 写窗口确实会让 UI 心跳停摆（时间戳对得上）
- 关掉写 = 不复位（因果成立）
- 蓝牙 buffer 风暴只是放大器，不是唯一根因（关写后风暴仍在，但不复位）

## 第三步：只读的代价要如实列出

只读不是免费的，必须明确告诉使用者：

- `health / steps / chat history / alarm / cron / bt_storage / persona / config` 写入全部失败，**读取正常**
- 重启后这些数据不保留
- App 侧的同步/写操作会失败
- 实时功能（语音、聊天、天气、TTS、BLE 连接）不受影响

## 第四步：恢复持久化的顺序

**不要一次全开。** 按"失败代价"从低到高，每步单独 soak：

1. `config` / `alarm`（小、低频、丢了可重建）
2. `health` / `steps`（低频）
3. `chat history`（最后，量最大）

每一步都要：写入后立刻读回校验 + 运行 30 分钟无复位，才推进下一步。

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 把看门狗超时调大 | 把"23 秒死机"变成"60 秒死机"，问题没变 |
| 上来就读文件系统代码 | 写窗口的阻塞点可能在 MTD/驱动，读上层代码读不出来 |
| 只加日志不复现 | 日志会改变时序，可能让问题消失——必须先建立稳定复现 |
| 一次性恢复所有持久化 | 出问题无法归因，等于重来一遍 |

## 一句话总结

> **先关掉嫌疑路径跑同样的负载**——如果故障消失，你省下了读三天代码的时间；
> 如果故障还在，你也省下了三天。

# 项目主的期望与我的历史错误

这份文件记录**被明确纠正过的地方**。目的是别在同一个地方再错一次。

---

## 一、项目主的四条核心要求

### 1. 「功能和创意优先，不是不断优化效果」

> 原话：「我觉得对于手表比赛来说，我们应该是功能和我们的创意优先，而不是不断有优化效果，
> 我们不可以打得过大厂的产品」

**含义**：不要花几天去把某个指标从 95% 优化到 98%。
**把功能做出来、能演示、有创意** 才是目标。

### 2. 「要真实的，不是演示」

> 原话：「我想要朝着真实的方向，而不是只为演示」

**含义**：
- 假数据要下线（`hr_monitor` 那种）
- 「返回成功但什么都不做」要如实标注出来
- 做不到的功能要么补上、要么**从界面摘掉**，不摆空壳

### 3. 「先真的找到问题，再继续」

> 原话：「还是没有，先真的找到问题后再继续」

**含义**：不要靠猜。**至少要有一条硬证据**才能动手改。
本仓真实有效的证据类型见 SKILL.md 的「先取证」一节。

### 4. 「先查官方文档 / 论坛，而不是自己试一试」

> 原话：「你应该先联网搜索看看有没有相关的，或在社区或者官方文档找到对应的内容，
> 而不是自己去试一试」

**含义**：遇到硬件/驱动层面的怪问题时，**先查 SiFli 官方文档、BBS、openvela 仓**，
别用试错法。

**真实代价**：IMU 的「弱上拉必须 <=100kHz」**就写在官方 I2C 应用笔记里**。
我一开始设 400 kHz，撞了整整一天、烧了十几版固件。

## 二、我被纠正过的具体点（按时间）

| 我说了什么 / 做了什么 | 实际情况 | 教训 |
|---|---|---|
| 建议用户「格式化 TF 卡」 | 用户理解成「你没经过允许就格式化」 | **措辞要精确**，涉及用户数据时先说清「我只是读，不会写」 |
| 报「烧录成功」 | 管道吃掉了退出码，其实 70ms 就退出了，什么都没烧 | 见 pitfalls P3 |
| 说 PA00/PA01 是「空闲引脚」 | PA01 是背光控制 | 见 pitfalls P4：用户的物理观察优先 |
| 用 `i2ctool` / 自写探针判断「设备不存在」 | 那个工具本身在这块板子上就是坏的 | 见 pitfalls P2：先验证工具 |
| 一次改多个文件再统一烧录 | 坏了不知道是哪一处 | 一次只改一层 |
| 改 A 弄坏 B（手势闸门让按钮全废） | 只验证「能启动」，没验证「按钮还能用」 | 每次烧录必须验证**上一个功能没退化** |

## 三、项目主的工作方式（观察到的）

- **会自己看板子、自己接线**，所以他的物理观察是最可靠的信息源
- **会追问「为什么」**，不喜欢「我觉得应该是」
- **会在关键节点叫停**（「先检查，后给我一个报告」）
- **接受「做不到」，但不接受「假装做到了」**
- 中文交流，**技术术语保留英文**（I2C、DMA、APB 等）

---

## 四、我该保持的自检习惯

每次报告「完成」之前，问自己：

1. **这个结论有证据吗？** 还是我在推断？
2. **我验证了「真的生效」吗？** 还是只验证了「编译通过/进程结束」？
3. **上一个功能还在吗？** 我有没有为了修 A 弄坏 B？
4. **有没有「假实现」被我当成了真实现？**
5. **说不确定的时候，我是真的说了不确定吗？** 还是含糊过去了？

## 五、绝对不允许的行为

- ❌ `git commit` / `git push`（**这个项目主明确要求不提交**）
- ❌ 没备份就大改（每轮大改前先 `fw.sh save vNN_pre_xxx_backup`）
- ❌ 报「成功」但没验证
- ❌ 把假数据/空壳说成「已实现」
- ❌ 在用户明确说「先查文档」之后还继续试错

# 02 血氧：一个只有算法骨架、还没有标定的答案

## 1. 先把这一章的边界钉死

血氧（SpO2）在这一章里是一个很奇怪的对象：它的代码从驱动配置到算法判据都是齐的，界面入口在应用列表里能点进去，LLM 工具也注册了，但**它从来没有在真机上产出过一次结果**。11-02 那份 1.64 MB 的串口日志里，`spo2` 这个词一共命中 9 次，9 次全是 `[tools] Registered tool: get_spo2` 这一行；`spo2:` 前缀的运行日志 0 条，`SpO2` 字符串 0 次（`.v3_work/logs/serial_ts.log`，grep 计数）。也就是说，工具在启动时被登记进了工具表，然后整场运行里再没有人触发过它，驱动的血氧函数也没有被调用过一次。

所以这一章只有一种诚实的写法：把算法讲透，同时把"没有结论"这件事本身讲成结论。本章会出现百分比的地方只有两类，每一处都当场标注性质——一类是把 R 值代进公式算出来的**演算值**，用来展示两套公式的差距；一类是页面上固定的参考档位，属于界面文案，不是测量结果。除此之外不存在第三种百分比，因为确实没有读数。

这样做不是自我贬低。`docs_ble/answer/_facts_baseline.md` §6.2 对这一栏的定性是"血氧读数仍出自同一颗 MAX30102，但未做多波长比值与佩戴压力标定，**不宣称血氧可用**"，§6.3 给出了标准句式："这块现在没做，方案在 X 号文档，下一步是 Y。"本章所有对外口径都从这两条派生，`_data_snapshot_v131.md` §4.2 又把红线收紧了一层：不得出现任何具体读数，不得把"可用/正常/准确"这类判断写进任何一句陈述。本章按此执行。

真正值得写进书里的是另一件事：这条链路在**代码层面**踩过并修掉了好几个真 bug，其中三个是 2026-10-19 对抗审查（`docs_ble/36_adversarial_review_and_revision.md`）确认的 P0；我逐行核对当前代码时又找出两处**还没修干净的地方**，它们会让"锁已就位"这个印象失效。这些发现比"我们实现了血氧"有信息量，因为它们描述的是一个真实系统在自己纠错时留下了哪些缝。

## 2. 血氧为什么比心率难：一个比值，两个通道，一个共同前提

心率要回答"一分钟跳几下"，做法是数峰：红光反射强度随血液容积波动，一个脉搏一个波峰，相邻波峰的时间间隔换算成 bpm。它只需要**一个通道**，信号形态也明确——一条有周期性的波形从噪声里被捞出来。`max30102.c` 的心率路径把这件事做得很细，去 DC、两级带通、包络、自适应阈值、RR 中位数，但所有这些都是围绕"找出周期性"展开的。

血氧要回答"血液里有多少比例的血红蛋白带着氧"，这是**成分**问题，而成分无法被直接测。能用的物理事实只有一个：氧合血红蛋白对红光吸收少、对红外吸收多，脱氧血红蛋白反过来。于是同时用两种波长照亮同一块组织，测两个通道的反射强度，两个通道的**波动比值**就能反推含氧比例。这就是 R 比值的来源，`max30102.c` §血氧段（`:3297`）的注释把它写成了两行公式：

```
R = (AC_red / DC_red) / (AC_ir / DC_ir)
SpO2 ≈ 110 - 25 * R
```

AC 是随脉搏波动的交流分量，DC 是由组织、静脉血、皮肤构成的静态基线。为什么不能直接拿两个通道的 AC 相除，而要各自先除自己的 DC：红光的 LED 亮度、光电二极管的增益、皮肤厚度、贴合压力都会让两个通道的原始幅度差出一大截，直接比 AC 比的是这些常数，不是血。`AC/DC` 是一个**归一化调制比**，把通道级的增益差异约掉，剩下的量才可比。这一步是整个算法的地基，也是后面所有"为什么必须同条件采样"的源头。

由此得到两个硬前提，它们不是实现细节而是物理约束：

**第一，必须双通道。** 只用红光（心率模式 `MODE_HR 0x02`）在物理上就算不出血氧，因为 R 的定义里缺一个未知数。所以血氧必须把器件切到 `MODE_SPO2 0x03`——RED 与 IR 同开（`max30102.c:361`，注释原文"血氧必须要双通道"）。

**第二，两个通道必须同时、同条件采。** 这就是 `MODE_SPO2` 下一个样本是 6 字节而不是 3 字节的原因：红光三字节与红外三字节打包在同一帧里被同一套时序采出来（`max30102.c:3475` 的注释"一个样本 6 字节: RED(3) + IR(3), 各自 18bit 大端"，解析在 `:3482-3483`）。如果两个通道错开采样、或者驱动电流差一档、或者手指在这个间隙里动了一下，两个 AC/DC 就不可比，比值失去意义。这条约束往下推，直接推出了三章之后要讲的所有工程：IR 驱动电流必须显式写、采样窗口必须够长且稳定、启动瞬态必须跳过、手指移动必须靠分段中位数吸收。

## 3. 硬件：MODE_SPO2、两个 LED，以及那个"定义了却从未写入"的电流

血氧模式的寄存器配置和心率模式共用一套时钟骨架，差别在三处。`SPO2_CFG 0x2F`（`:363`）设的是 4096nA 的采样电流、400Hz 采样率、411us 脉宽（18 位）；`FIFO_CFG 0x5F`（`:364`）是 4 样本平均加 rollover 加 A_FULL=15。两者相乘的结果是输出样本率 100 sps：400Hz 采样被 4 次平均降到 100（`:18-20` 文件头注释、`:375` 与 `:514` 的 `HR_FS_NOMINAL 100.0f` 三处互相印证）。血氧路径沿用了同一套采样配置，没有另起一套，这是刻意的——同一颗芯片在同一时钟配置下换模式，能少一套标定变量。

三处差别里，第一处是 `MODE_CONFIG` 从 `0x02` 换成 `0x03`；第二处是每样本从 3 字节变 6 字节；第三处是 **IR 的驱动电流寄存器 `REG_LED2_PA 0x0D` 必须被写**。第三处正是那个 bug 的位置。`max30102.c:299` 这一行如今是这样写的：

```c
#define REG_LED2_PA       0x0D      /* IR LED 驱动电流 —— 旧代码定义了但**从未写入** */
```

宏定义了，值也想过，但初始化流程里没有任何一条语句把它写进芯片。这个 bug 的形态很典型：**代码审查能审"写出来的东西对不对"，审不出"该写的没写"**。它没有报错、没有编译警告、心率功能完全正常，因为心率只用红光，红光电流 `REG_LED1_PA` 一直是写了的。只有在切到血氧模式时才暴露：IR 通道的驱动电流停留在芯片上电默认值或上一次的残留值，红外反射强度要么太暗、要么贴顶饱和，无论哪种，R 的分子分母里都有一个不可信的项。

发现它的路径是对参考初始化序列做差集，而不是再读一遍自己的代码。这一点在工程上比 bug 本身更值得记：当一个器件"该亮的没亮、该有的没有"时，唯一有效的排查方式是把器件手册或成熟实现的初始化序列逐条列出来，与自己的写入序列做集合差，缺哪条一目了然。项目里另一个同型案例是麦克风驱动漏调 `HAL_TURN_ON_PLL`，四轮人工审查没找到，因为缺的那条调用不在任何被审的代码行里。

修法在 `max30102.c:3437-3438`，进入血氧采集前显式写两个寄存器，顺序是先电流后模式：

```c
if (i2c_write_reg(g_hr.fd, REG_LED2_PA, SPO2_LED2_PA) < 0 ||
    i2c_write_reg(g_hr.fd, REG_MODE_CONFIG, MODE_SPO2) < 0)
```

`SPO2_LED2_PA` 取 `0x2F`（`:3317`），注释理由是"与红灯同档"——两通道驱动电流接近，归一化调制比的基准才一致。红光这边则调过一次档：`max30102.c:365-369` 记着真机上 `dc≈207659`（接近 18 位满量程 262143 的八成）同时 `ac_pp=0`，即交流分量为零、信号贴着量程顶被切平，于是按数据手册 Table 8 把 `LED_PA` 降到 `0x2F`。这里的判断值得单列：**"信号很强"不等于"信号很好"**。幅度大而 AC 为零是饱和的指纹，不是灵敏度的表现；区分两者看的不是绝对值大小，而是 AC 与 DC 的比例是否落在生理范围。

这一节的收尾要留一个诚实的注脚。同一段注释里写着 `0x2F` 是"9.4 mA"，紧接着又写"从 12.6mA 降到 6.2mA"，而 `max30102_init` 成功时打印的文案是"LED=12.6mA"（`:1092-1094`），真机日志里同一行同时出现 `0x0c=2f` 与 `LED=12.6mA`（`.v3_work/logs/serial_ts.log` 15:50:48 那条 `init OK`）。按 Table 8 的 0.2 mA/LSB 换算，`0x2F=47` 对应约 9.4 mA，因此这三处里有两处是错的：注释里的"6.2mA"与打印文案里的"12.6mA"都没跟上改档。这不影响功能（真正生效的是写进寄存器的 0x2F），但它说明日志里的文字不可当作证据，判断电流只能看回读值。

## 4. 采集：一轮为什么是十九秒，以及这个十九秒里真正发生了什么

`max30102.c:3313-3317` 把采集窗定死：

```c
#define SPO2_ROUNDS        300     /* 轮询轮数, 每轮 50ms => 约 15s 采集 */
#define SPO2_POLL_MS       50
#define SPO2_PER_POLL      4       /* 每轮最多取 4 个样本 */
#define SPO2_MIN_SAMPLES   200     /* 少于这么多样本不出结论 */
```

300 轮乘 50 ms 等于 15 秒，这是**硬件采集窗**。但用户感受到的一轮是约 19 秒，差的这 4 秒不在传感器里，在 `spo2_measure.c:105-109`：

```c
for (i = 0; i < 4; i++) {
    s_progress_left_s = 20 - i * 5;
    lvgl_ui_post(progress_async_cb, NULL);
    usleep(1000 * 1000);
}
```

worker 线程先睡四秒，每睡一秒把进度文本从 20 递减到 5，然后才去调真正的采集。这个设计在 `docs_ble/34_auto_health_design.md` §1.3 里被明确记过一笔："血氧 15 s 硬件 + 4 s 假进度 = 19 s"，紧接着该文纠正了作者自己先前的说法（"我之前的说法要更正：我说血氧 19 秒是硬件耗时——错"）。所以对外讲这一轮的长度时，必须拆成两段说：15 秒是常量决定的采集窗，4 秒是本地为了"让用户看到还在跑"而加的等待，两者相加约 19 秒，工具文案里的"约20秒"（`tool_health.c:185`）取的是这个整数上界。

这四秒假进度还带来一个真实的界面缺陷：进度从 20 一路减到 5 之后就不再动了，而此时硬件采集才刚开始，屏幕上会停在"测量中 5s"这一帧，实际还要等 15 秒。也就是说最后三个多进度步长（从 5 到 0）从来没被走完，用户看到的是一个**比真实剩余时间乐观得多**的倒计时。它不致命，但它属于"界面在撒谎"这一类问题，与全书反复强调的诚实性同源——只是这里撒的谎很小，没人会在演示时被抓。

采集窗内部的样本账比常量看上去复杂。产出侧是 100 sps 乘 15 秒，理论上 1500 个样本；读侧每 50 ms 最多取 4 个，即最高 80 sps，**低于产出率**。差值不会消失，会进 FIFO——FIFO 深度 32（`:411-415` 注释"上限 32 = MAX30102 FIFO 深度"），而 `FIFO_CFG 0x5F` 开了 rollover，溢出时旧样本被新样本覆盖。所以稳态下血氧路径读到的是约 1200 个样本（300 轮乘 4），其中 200 个在稳定期被丢掉（`:3491-3495`），真正进入统计的约 1000 个，分 50 个一段，得 20 段左右，而 `SPO2_SEG_MAX 24` 这个上限从来没被填满过——它是留给"总线更快、门控更少空转"时的余量。

还有一处能力差异容易被忽略：血氧路径**根本不读溢出寄存器**。整个采集循环（`:3452-3528`）只读 `REG_INT_STATUS1` 判断有没有数据、再读 `REG_FIFO_DATA`，`REG_FIFO_OVF 0x05` 只在进入前被清零一次（`:3446`），之后再没被看一眼。心率路径对 0x05 有一套"只记账、不清零、不触发恢复"的成熟处理（`max30102.c:2340-2400` 的大段注释），血氧路径没有继承这套。后果是：欠采样与 rollover 在血氧侧是完全静默的，你无法从日志判断这一轮到底有没有丢样。这与"比心率更容易"的直觉相反——血氧路径的观测能力比心率路径更弱。

再往下是阈值的问题。`SPO2_MIN_SAMPLES 200` 等于 2 秒的数据，`nseg >= 3`（`:3557`）等于 1.5 秒，两道门槛的联合效果是**允许用两秒数据出一个结论**。而采集窗之所以设计成 15 秒，理由写在注释里：多个心动周期取平均，让 AC 估计的抖动被中位数吸收。门槛与意图之间差了一个数量级——它防住的是"手指没贴"这种极端情况，防不住"贴了但只贴了两秒"。这是设计上的一处松紧不一致，源码里没有解释为什么 200 而不是 800。

采集窗长度还有两个方向的约束在拉扯。下限是统计稳定：静息心率 60–100 bpm 对应 0.6–1 秒一个周期，15 秒覆盖 15 到 25 个周期，够做中位数；上限是用户耐心，手指要贴稳不动，15 秒已是消费级设备能要求的边界，`s_progress_left_s` 存在的全部意义就是让用户知道还剩多久、别中途松手。而每轮 50 ms 的轮询周期不是随便取的：`max30102.c:374-384` 说清了两件事——输出 100 sps 时 50 ms 会积 5 个样本，FIFO 深 32 离溢出（320 ms）很远；而 10 ms 一轮会把"读状态、读溢出、读指针、读样本"这套动作压在 100Hz 上重复，总线负载是 50 ms 一轮的五倍。本板总线是"拼接 SCL + 只有 SoC 内部弱上拉"的边际状态（`:183-207` 的 pinmux 注释、`:238` 的 50kHz），降负载直接换电气余量。所以这个时长不是算法定的，是**常量加总线余量共同定的**；端到端从按下按钮到出数的总耗时，项目从未作为指标测过，本章不给数字。

## 5. 五个处理步骤：稳定期、分段、峰峰、中位数、比值

从 1200 个原始样本到最终那个 R 值，中间有五个处理步骤，每一步都在削掉一类特定的污染。

**第一步，跳过启动稳定期。** `SPO2_SKIP_SAMPLES 200`（`:3332`）意味着前 200 个样本（约 2 秒）被直接丢弃（判断在 `:3491-3495`），不计入 DC、不计入分段。理由是第一次实测打出来的数据：不跳稳定期时，RED 通道 `dc=151454`、`ac=70171`，调制比 46%。而真实 PPG 的 AC/DC 只有 1~5%，最多到 10%。46% 不是脉搏，是三重瞬态的叠加——IR LED 第一次点亮后电流与光通量还在建立、光电二极管前端的工作点还在恢复、手指接触压力在最初两秒里变化最快导致 DC 基线还在重新建立。三件事叠在同一个窗口里，任何"从第一个样本就开始统计"的实现都会被这段数据污染。跳过的代价是丢掉 2 秒，收益是让之后的统计落在准稳态上，这笔交易很划算。

**第二步，按段求峰峰值，而不是对整段求全局峰峰值。** `SPO2_SEG 50`（`:3333`）即每 50 样本约 0.5 秒一段，段内取最大值减最小值，存进 `seg_r[]`/`seg_i[]`。这一步是整个算法里最关键的设计判断，注释里留着证据（`:3326-3330`）：第一次实测用整段 min/max 得到 `min=82666 max=152837`，"近乎 2 倍摆动"。手指压力变化会改变组织厚度，进而改变透光量，于是 DC 基线在 10 秒里缓慢漂移；全局 min 可能来自压力最大的一刻、全局 max 来自压最小的一刻，两者之差量的是**压力变化**，跟脉搏无关。切成 0.5 秒之后，段内漂移可以忽略，因为漂移是慢变量、脉搏是 1Hz 量级的快变量，0.5 秒里正好容纳一两个完整周期；段与段之间的漂移交给下一步吸收。

**第三步，对段峰峰值取中位数。** 两个通道的段数组各自做插入排序（`:3564-3581`），各取下标 `nseg/2` 的值作 AC（`:3583-3584`）。中位数在这里的价值很直接：如果 20 段里有三五段因为手指动了一下变成伪迹，中位数不会被拉高，平均值会被。注释的说法是"对某一段有动作伪迹免疫"。用插入排序而不是快排不是算法偏好，而是 `nseg ≤ 24`，规模小到插入排序的实际耗时更低、代码更短、没有递归，纯务实选择。

**第四步，算调制比并做生理范围检查。** DC 是全部有效样本的均值（`rsum/n`、`isum/n`，`:3550-3551`），AC 是中位段峰峰，两者相除得 `mod_red`、`mod_ir`（`:3597-3598`）。然后是一道硬门槛（`:3603-3611`）：两个通道的调制比都必须落在 `0.003~0.15`，即 0.3% 到 15%。代码注释解释得很直白：第一次实测得到 46%，那明显不是脉搏；这里把"调制比不合理"显式判为信号不可用，而不是硬算一个 SpO2 出来。这是本章最核心的工程价值观——做传感器功能最大的诱惑是"只要采到数据就出个数"，因为数字看起来像功能完成，但一个错误的数字比一句诚实的失败提示更糟，前者会被用户相信并据以行动。

**第五步，算 R 并做第二道范围检查。** `ratio = mod_red / mod_ir`，要求落在 `0.3~1.5`（`:3618-3622`）。这道检查比上一道更细，它拦的是"两个通道各自都在生理范围内、但比值不合理"的情形——典型来源是一个通道正常、另一个通道饱和或过暗，此时两个调制比可能都合法，比值却跑出界。至于为什么要收得比参考实现更严，见 §6。

有一个问题源码没有回答，而读者一定会问：**为什么 AC 用峰峰值而不用 RMS？** 全文件搜不到任何一处解释这个选择，所以下面是从信号处理出发的分析，不是源码记载，读的时候要分清。RMS 描述的是波形的能量，它依赖波形的形状与占空比；PPG 的波形形状随心率、血管弹性、佩戴压力变化，同一个峰值幅度可以对应不同的 RMS，用 RMS 相除等于把波形形状的差异引进 R 里。峰峰值则直接对应调制的包络幅度，物理含义是"一个心动周期里透光量的最大变化量"，与 R 的定义同量纲。反面代价也真实：峰峰值对单个噪声尖峰极其敏感，一个毛刺就能把某一段的峰峰值抬到天上去。所以峰峰值与"分段+中位数"必须成对出现——单看任一半都是坏的，合起来才是完整的。这也能解释为什么代码里没有任何滤波预处理：它不需要靠滤波压噪，它靠段内峰峰+跨段中位数把单点异常投票掉。

## 6. R 到 SpO2：那条缺席的标定曲线

所有前置判据都过了之后，才进入换算（`max30102.c:3624-3630`）：

```c
/* 110 - 25*R 是通用端点近似, **未按本模块标定** —— 只作参考 */
spo2 = 110.0 - 25.0 * ratio;
if (spo2 > 100.0) spo2 = 100.0;
if (spo2 < 70.0)  spo2 = 70.0;
printf("spo2: SpO2 ~ %.0f%%  (未标定估算; 物理量 R=%.3f 更可信)\n", spo2, ratio);
```

用的是 `SpO2 = 110 − 25R`，一条线性经验式。代码注释自己写明"未按本模块标定、只作参考"，而打印文案更进一步，直接把"R 更可信"写进了运行时输出。这不是事后补的解释，是代码里就有的判断：**R 是直接测出来的物理量，百分比是经一条未标定公式换算出的推断量**，两者的可信等级不同。

`docs_ble/35_auto_health_design_v2.md` §3.4 记录了这组数字的来龙去脉，给了两套公式的对照：

| 来源 | 公式 | R=0.475 | R=0.650 |
|---|---|---|---|
| 我们现在的 | `SpO2 = 110 − 25R` | 98.1% | 93.8% |
| Maxim 参考算法 | `SpO2 = −45.06R² + 30.354R + 94.845` | 99.1% | 95.5% |

**这张表里那四个百分比是把 R 代进公式算出来的数，不是任何一次测量。** 它们的作用只有一个：显示同一 R 下两套公式差 1~2 个百分点，从而说明"公式选择本身就能带来这个量级的偏差"。同一节的原话是"差 1~2 个百分点。两套都是经验拟合，**都没有按我们的模块标定**""血氧只适合做趋势 + 阈值告警，不要当临床数值"。本章引用这张表时，请读者也按这个性质读它。

为什么"没标定"是硬缺口而不是能糊弄过去的小事，原因在标定这件事本身的性质。R 到 SpO2 的关系不是物理定律，是**经验拟合**。不同厂家的传感器，LED 中心波长、光电二极管响应曲线、封装光学结构、LED 与探测器的间距都不同；同一 R 值对应的真实血氧会有系统性偏差，偏差量随个体（肤色、指甲、组织厚度）还会再变。要得到可信百分比，必须用参考设备做对照：在多档血氧水平、多种佩戴压力下同时测，采到 R 与参考值的对应点，拟合出这颗模块专属的曲线。项目一次都没做（`docs_ble/37_real_health_roadmap.md` §0 的五条可证伪标准里，第 2 条"准确性"的状态就是"从未做过"）。

两处钳位也说明同一件事：上限 100%、下限 70% 只防外推出荒谬值，不提高精度。它真正做的事是把超出区间外的失真藏起来——R 跑到很小时公式会给出 100 以上的数，钳到 100 之后看起来"很正常"，但那个数背后的外推误差一点没少。所以钳位是显示层的保底，不是算法层的修正，不能当成精度手段。

## 7. 有效性判据的三层：每层拦一类失败

散在各处的检查归拢起来，"这次结果有效"要过三层，每层针对不同的失败模式。

**数据层**：样本数 `n >= 200`（`:3542-3547`）、有效分段 `nseg >= 3`（`:3557-3561`）、两个 DC 都非零（`:3591-3595`）。这层拦的是"根本没采到"和"LED 没亮"：`n` 太小意味着手指没贴稳或器件没工作，DC 为零意味着光路根本没通。报错文案很直白——"样本太少(n=%u, 需要 >=%u) —— 手指没贴稳或 LED 没亮"。

**物理层**：两个通道的调制比都落在 0.3%~15%（`:3606-3611`）。这层拦的是"采到了、但采的是漂移或伪迹"。它是三层里最年轻的一层，是被第一次实测的 46% 逼出来的；它也是唯一一层同时约束两个通道，因为 R 的可信度要求两个分子分母都干净。

**生理层**：R 落在 0.3~1.5（`:3618-3622`）。这层拦的是"调制比各自合法、比值不合法"。为什么比参考实现收得更严，`docs_ble/35_auto_health_design_v2.md` §3.4 给了判断：Maxim 参考算法的有效区间是 `R ∈ [0.02, 1.84]`，我们用的是 `[0.3, 1.5]`（对应约 100%~72%），文档自己的评价是"对消费级只报趋势来说，更严是合理的"。道理在于，R 越靠近端点，线性近似的外推误差越大；消费级设备上出现极端 R，更可能意味着信号链某处不干净，而不是用户真的处在生理极端。

三层全过，才把 `g_max30102_spo2_ok = 1`，同时填 `g_max30102_spo2_r` 与 `g_max30102_spo2_pct`（`:3634-3636`）。注意代码注释对 `ok` 的定义是"本次结果有效(调制比/R 都合理)"——它说的是**信号质量合格**，不是"这个百分比在临床上可信"。这个语义差是后面 UI 出问题的根源（§11）。

`ok` 为 0 时上层必须显示"信号不可用"，不能显示 0% 或任何编造值。这条纪律与心率侧的"测不到就不显示"同源。还有一个 flat build 特有的坑：每轮开始前必须先清三个全局量（`:3389-3391`），否则上层会读到上一轮的旧值——应用不是"重新加载"，只是同一二进制里的函数再跑一遍，static 变量跨轮保留。这与文件里 `g_hr_pub` 那段注释记的是同一类陷阱。

## 8. 架构约束：不能阻塞渲染线程，结果不能走返回值

血氧有一个别的模块没有的约束：它绝对不能在 LVGL 的渲染线程上执行。本工程 LVGL 以 `LV_OS_NONE` 构建（`out/nuttx_contest_board_ai_agent/.config:3596` 的 `CONFIG_LV_OS_NONE=y`），渲染线程是唯一碰 LVGL 的线程，`lvgl_ui_channel.c:214-220` 的注释把后果写得很清楚："LVGL is built with LV_OS_NONE here: no internal locking. Calling lv_async_call() ... from agent/key/NSH threads races with lv_timer_handler() on the render thread and can corrupt the timer list."。渲染线程每 5 毫秒一轮（`RENDER_PERIOD_US 5000`，栈 `RENDER_STACK 32768`），整个界面的活性都挂在这个循环上。在这个线程里阻塞 19 秒，用户看到的就是界面彻底定格。

所以点击回调只做一件事：调 `spo2_measure_start()`。它检查单飞标志 `s_busy`（`spo2_measure.c:150-156`），用 `pthread_create` 起一个 detached worker（`:158-163`），立刻返回。真正的 15 秒采集与 4 秒等待都在 worker 里。这个函数内部不碰 LVGL，`spo2_measure.h:14-16` 的调用约束写的就是这一条。worker 栈 `SPO2_STACK 16384`（16KB）。

第二个约束是结果怎么传回来。`spo2_measure.c` 文件头第二点（`:11-13`）解释：`hr_sensor_main` 是 `main()` 形态，只返回 int，具体数值由 `max30102.c` 的 `spo2_measure()` 填进 `g_max30102_spo2_{r,pct,ok}`；两边同在链接行的 `--start-group` 里，全局符号可以互相解析。于是数值只能走全局变量——这是被 `task_spawn` 机制逼出来的，不是设计偏好。代价是残留：跨轮必须手动清零，否则上一轮的值会被当成本轮（§7 末尾）。

第三个约束是内存，这里要把一个容易被讲错的账算清楚。静态占用按基线口径是 **94.7%**（bss 480,984 + data 15,272 = 496,256 B / 524,288 B，基线 §5；v131 实测已升到 95.2%，仍在涨），留给内部 SRAM 的余量只有两万四千多字节。但**线程栈分配在堆上，不在静态区**，而本板的堆主体在 8 MB PSRAM：启动日志里 `[agent] [boot +141ms] heap: arena=8397544 free=8267336 used=130208`（`.v3_work/logs/serial_ts.log` 15:49:41，arena 约 8 MB 对应 PSRAM 容量，`vendor/sifli/chips/sf32lb52/sifli_allocateheap.c:70-71` 定义 `PSRAM_START 0x60000000` / `PSRAM_SIZE 0x00800000`）。所以严格地说，16KB worker 栈是从 8 MB 的 PSRAM 堆里划的，**不构成硬约束**；紧的是内部 SRAM 那 95.2% 的静态占用，它限制的是"还能不能再加全局缓冲/大数组"，不是"能不能再起一个 16KB 栈的线程"。这个区分很重要——把 16KB 栈说成"从 95.2% 的余量里抠出来"是错的，会让人误判后续给功能加缓冲的空间。真正给不起的是**常驻**开销：连续监测要常驻线程加长期缓冲，那才是 95.2% 静态占用 + 25KB 内部余量真正拦住的事。

第四个约束更隐蔽：`SPO2_PRIORITY 100` 这个宏定义了却从未被使用（`spo2_measure.c:48`，全工程 grep 只有定义处一次），`pthread_create` 前后没有任何设置优先级的调用。所以 worker 实际跑在默认优先级上，"优先级 100"是一句写在文件里但没有生效的话。它不影响功能，但说明这份代码里存在"文档写了、代码没做"的同类问题——和 §3 的 IR 电流 bug 是同一个家族，只是后果轻得多。

为什么不让血氧复用心率那条常驻采集线程？三条都不成立。心率采集线程是 uORB 话题 `algo_heartrate` 的发布者、有自己的热路径与恢复逻辑；血氧是一次性顺序流程，没有常驻线程也没有 stop 请求要送；两者共用一颗芯片，复用线程等于把两种语义塞进同一个状态机，还要处理"采集中途切换模式"。`spo2_measure.c:79-84` 的注释对最后一条给了明确选择：直接在本线程同步调 `hr_sensor_main`，不走 `task_spawn`，"spo2 是纯顺序流程，没有常驻采集线程，不需要把 stop 请求送进另一个任务"。

## 9. 资源互斥：一颗芯片，两个主人，一把放在驱动层的锁

心率与血氧不是两颗传感器，是同一颗 MAX30102 的两种模式。这个物理事实是所有竞态的源头。修复前的形态在 `docs_ble/35_auto_health_design_v2.md` §4 与 `36_adversarial_review_and_revision.md` §1 里记录得很完整：血氧入口只**查** `g_hr.running`，自己**从不置** `running`，只置 `inited`。这个不对称造成两条恶果。一条是血氧测量进行中点测心率时，`inited` 为真于是 `hr_start` 跳过 open+init，直接拿着 `MODE_SPO2` 的六字节样本流按三字节解析，相位全错，读出来的是"格式合法、物理无意义"的垃圾；同时两个流程抢同一个 FIFO 指针。另一条更狠：心率采集线程退出时写 SHDN 关灯（现 `:2804`），直接把血氧正在用的 LED 灭掉。

修复不是加一个 busy 标志，而是在驱动层加所有权仲裁。`max30102.c:301-314` 的注释把理由写透了：锁必须放在**唯一真正碰硬件的地方**，因为 `hr_sensor start` 与 `spo2` 本身还是 NSH 内建命令，命令行会绕过任何只写在按钮回调里的检查；只有把锁放驱动层才能覆盖全部入口（按钮、工具调用、后台守护、串口命令）。枚举与实现（`:316-348`）：

```c
typedef enum {
  SENSOR_OWNER_NONE = 0,
  SENSOR_OWNER_HR,        /* hr_start 起、采样线程退出止 */
  SENSOR_OWNER_SPO2,      /* spo2_measure 全程 */
} sensor_owner_t;
```

语义是同一 owner 可重入、不同 owner 返回忙。`hr_start` 在 `:2846` claim，采集线程退出路径在 `:2814` release（放锁必须在线程退出时而不是 `hr_stop` 里，否则会留出"线程还没关灯、锁已经放掉"的窗口）；`spo2_measure` 在 `:3401` claim，统一收尾在 `:3654` release。这条设计原则可以推广：**互斥要留在最靠近物理资源的那一层**；应用层的互斥只是"用户操作互斥"，驱动层的互斥才是"物理使用者互斥"。

为什么光有 `g_hr.running` 不够，`spo2_measure.c` 注释（`:3399-3400`）点了名：`running` 是在 init **之后**才置位的，而 init 正常要几百毫秒、坏总线可达数秒，这段窗口里血氧看 `running=false` 也会启动。这是典型的 TOCTOU，只有所有权锁能从根上堵住。

以上是修好的部分。逐行核对我又找到两处**还没修干净**的缝，它们让"锁已就位"这句话打折扣。

**第一处，claim 之后有两条裸 return 没有 release。** `:3401` claim 成功后，`:3418` open 失败会在 `:3422` 直接 `return 1`，`:3425` init 失败会在 `:3430` 调 `sensor_power_off()` 之后于 `:3431` 直接 `return 1`。这两条路径都没有 `sensor_release(SENSOR_OWNER_SPO2)`——全函数里 release 只出现在 `:3654`，而它只有 `out_fail`/`out` 这两条 goto 路径能到达。后果：只要一次 open 或 init 失败，`g_sensor_owner` 就永久停在 `SENSOR_OWNER_SPO2`，之后所有 `hr_start` 都会打印"传感器被血氧测量占用, 稍后再试"、所有后续血氧也会被自己挡回去，**功能只能靠重启恢复**。这不是理论风险：本板 I2C 是"拼接 SCL + 内部弱上拉"的边际状态（`:183-207`），open/init 失败不是小概率。`36_adversarial_review_and_revision.md` §4 的验收标准写的是"SHDN → close → `fd=-1` → `inited=false`，**覆盖全部 7 个出口**"，当前代码把 7 个出口压成了两条 goto 路径，但 claim 之后仍有两条逃逸。

**第二处，`hr_selftest` 完全不 claim。** `hr_sensor selftest` 这个诊断子命令在 `:3072` 自己 `open` 了同一个设备节点，`:3167` 会往 `REG_LED1_PA` 依次写 `0x3f`/`0x00`/`0x3f` 做写-回读对照，最后 `:3289` close。这条路径既没有 `sensor_claim`，也不检查 `g_sensor_owner`。也就是说，如果在血氧 15 秒采集窗里从 NSH 敲一条 `hr_sensor selftest`——一条完全合法的诊断命令——它会临时把红光 LED 电流改成 `0x3f`（12.6 mA）再改回，中途还写 `0x00`（灭灯）。红光电流在采集中被改三次，这一轮的 R 分子就彻底不可信，而没有任何一方会报错。这就是"锁覆盖了 start 和 spo2，却没覆盖 selftest"的具体后果。

把这三层合起来看，当前状态是：锁的方向对了，主路径修好了，但**入口覆盖与失败路径覆盖都还有洞**。这比"已修复"更准确，也更值得写进书里——因为下一个改这块代码的人需要知道该补哪里。

## 10. 一轮测量的完整时序

先把入口说对。应用列表「血氧」气泡（`applist_page.c:82`，`APPLIST_APP_SPO2`）→ `ui_nav.c:123-124` 路由到 `UI_PAGE_SPO2` → `ui_nav.c:202-203` 调 `spo2_page_create()`。宠物页那两个"测心率/测血氧"按钮在 v131 **已经被移除**：`pet_page.c:645-646` 的注释写着"原「健康」第二屏（测心率 / 测血氧按钮）已移除：这两个功能现在各有独立页面，从应用列表进入"；与该注释一致，`pet_page.c:387` 里那个 `on_spo2_measure_clicked` 既没有注册到任何 `lv_add_event_cb`（全文件只有两处 add_event_cb，都在容器与云朵上），编译产物里也找不到它的符号（`arm-none-eabi-nm` 对 `pet_page.c.o` 只列出 `on_back_clicked`、`on_cloud_clicked`、`cloud_voice_thread`）。所以任何"点宠物页血氧按钮"的描述对当前固件都是错的，正确入口是应用列表和语音/工具。

从按钮开始，一轮的路径是这样的。血氧页的 `on_measure_clicked`（`spo2_page.c:100-127`）先把 `s_measuring` 置 1、按钮改"测量中…"、状态改"测量中…保持手臂静止"，然后调 `spo2_measure_start()`；返回 `-EBUSY` 表示已有一轮在跑，页面继续等它的结果，其余错误立刻回落到"测量失败，请重试"。

worker 内部的步骤是串行的：跑那四秒假进度 → `sensor_claim(SENSOR_OWNER_SPO2)` 拿所有权 → `open("/dev/i2c1")` 并 `max30102_init()` → 写 `REG_LED2_PA` 与 `MODE_SPO2` 切双通道 → 清 `FIFO_WR_PTR / OVF / RD_PTR` 三个指针（`:3445-3447`）→ 进 300 轮采集循环。其中 open + 初始化这一步**每次都要重做，不能用 `g_hr.inited` 做守卫**：`:3407-3417` 的注释记录了 2026-10-18 踩到的坑，flat build 里上一轮进程退出时内核已关掉 fd，用 inited 守卫就会拿着失效编号去写寄存器，表现为"第二次起配置 MODE_SPO2 失败"。

采集循环（`:3452-3528`）每轮先睡 50 ms，读 `REG_INT_STATUS1` 判断数据位，`(st & 0xC0) == 0` 就跳过这一轮，否则最多读 4 个六字节样本、解码成两个 18 位值、丢掉任一为零的样本、计 `nseen` 跳过前 200、更新段内 min/max、满 50 个记一段峰峰。循环跑完进判据链：样本数 → 分段数 → DC → 调制比 → R，任何一条不过就 `goto out_fail`，`ok` 保持 0。

全过则算 `110 − 25R`、做两处钳位、填三个全局量。收尾只有一处：`sensor_power_off()`（写 SHDN 关灯 → `close(fd)` → `fd = -1` → `inited = false`，`:3359-3371`），然后 `sensor_release`。worker 读回全局量，`ok` 为真时组织"您的血氧是 NN%"经 `lvgl_ui_channel_send_kind(text, AGENT_MSG_KIND_FINAL)` 推出去，失败时推"血氧测量未成功，请把手指贴稳传感器"并按 ERROR 类型处理（`spo2_measure.c:113-130`），之后放掉 `s_busy`。`greeting_restore_async_cb`（`:72-77`）是空函数，结果是刻意留在屏幕上不抢回问候语的。

这个时序里有两处顺序是有讲究的，都不是风格问题。**FIFO 清零必须在切模式之后**：清在切模式之前，清掉的是心率模式的残留指针，切完模式新样本又堆进来，第一批统计里就会混进切换瞬间的样本。**关硬件必须在放锁之前**：反过来的话，下一个 owner 可能在我们还没关灯时就进了 `hr_start`，又变成两个流程抢同一颗传感器——`spo2_measure()` 的 `out:` 注释（`:3646-3652`）专门记了这一条。

## 11. 数据怎么到 UI 和工具

血氧结果有三条消费路径，而现有实现把这三条的性质讲得不够清楚，这是本章要指出的第二类不一致。

**页面上屏走全局变量直读。** `spo2_page.c` 在 `:48-49` 直接 `extern` 了 `g_max30102_spo2_pct` 与 `g_max30102_spo2_ok`，用一个 500 ms 的 `lv_timer`（`:303`）在 `refresh_cb`（`:133-195`）里轮询：`s_measuring && !spo2_measure_busy()` 时认为这一轮结束，若 `ok` 且 `pct > 0` 就把取整后的值写进 88px 大数字，否则把主值清成 `--` 并写"测量失败，请重试"。这里有一条做对了的细节（`:147-157`）：没测过就显示 `--` 而不是 0，因为 0 会被误读成"测出来是 0"。页面底部另有一行固定的参考档位，文案本身标了"（非诊断）"，与"本次结果"分属两个 label——`:22-24` 的注释说这是 2026-11-03 拆开的，原来两件事挤在同一个 label 里，会出现"主值是 `--` 却写着参考范围"的误导。

**气泡与语音走消息通道。** worker 用 `lvgl_ui_channel_send_kind`（`lvgl_ui_channel.c:1113-1150`）把文本交给渲染线程；`AGENT_MSG_KIND_FINAL` 会进历史、更新气泡，并触发 `voice_channel_speak_async()` 念出来，非 FINAL（错误语、状态语）只上屏不念——`lvgl_ui_channel.c:1128-1136` 的注释把这条"显示了不等于要念"的解耦点写得很明确。

**工具走 `get_spo2`。** 注册在 `tool_registry.c:435-440`，实现在 `tool_health.c:168-198`。它的策略是：`g_max30102_spo2_ok` 为真就回"您上次测的血氧是%d%%"并直接返回；否则起一轮测量，回"血氧测量已开始，约20秒后播报结果，请把手指贴稳传感器"；`-EBUSY` 回"上一次测量还在进行中"。注释解释了为什么工具绝不自己同步等：那会把 agent worker 卡住二十秒（`tool_health.c:155-167`）。

以上三条都能跑，但它们各自对"未标定"这件事的处理方式不一致，构成了当前最值得改的地方。

页面在 `:177-184` 用一个固定阈值把结果二分成两档：高的一档写"本次测量有效"，低的一档写"偏低，建议复测"。问题有两层。第一层是语义混淆：`ok==1` 在算法层的含义是"调制比与 R 都合格"，即**信号质量通过**，不是"这个百分比本身有效"；把它写成"本次测量有效"，读者会把"有效"理解成"数值可信"。第二层更硬：用一个**固定阈值**去判断高低，等于在未标定的百分比上做绝对判断。而 `docs_ble/36_adversarial_review_and_revision.md` §2.3 的结论恰恰是"标定前只能做趋势和「信号不可用」，不能做绝对百分比告警"，理由写得毫不含糊——一个未标定的阈值判断，比没有判断更危险。页面这一行代码正撞在这条结论上。

工具与语音那条路径也有一处同源的问题：`tool_health.c:176` 与 `spo2_measure.c:115-121` 都会把取整后的百分比当成事实报出来（前者"您上次测的血氧是%d%%"，后者"您的血氧是 NN%"并经 FINAL 触发 TTS 朗读），话里没有任何"未标定/仅供参考"的限定。算法侧在串口日志里是诚实的（打印文案带"未标定估算"），但**用户听到的那句话没有带**。这是全书反复强调的那条纪律在最后一米失效的典型位置。

第三处不一致是进度回显的去向：`progress_async_cb`（`spo2_measure.c:60-70`）写的是 `pet_page_update_response`，也就是宠物页的 AI 文本层，而这一轮测量是从血氧页发起的。血氧页自己的"测量中…"状态来自它 500 ms 的定时器，与那四秒倒计时无关。结果是用户站在血氧页上，看不到任何秒数倒数；那串"测量中 20s→5s"的文本落在另一个页面上。这个问题不影响正确性，但它说明进度这条链路的两端没有对齐。

## 12. 现在能说什么、不能说什么

总结口径时要把状态与边界放进同一句话，这是基线 §6.2 的写法，也是唯一经得起追问的写法。

**可以说**：血氧算法链路代码齐备——RED+IR 双通道采集（`MODE_SPO2 0x03`）、R 比值计算、跳稳定期、分段峰峰中位数去漂移、三层有效性判据、会话级清零防残留；UI 入口（应用列表 → 血氧页）与 `get_spo2` 工具都在；算法对"信号不可用"有多道显式拦截，物理量 R 的可信度高于换算出的百分比——**但整条链路未做真机标定、未做对照验收，也没有任何一次真机读数**。

**不能说**：任何具体读数；把这项功能描述为可用、正常或准确的；声称它能预警低氧；把两套公式的演算结果（如 98.1% 与 93.8%）当作测量结论。理由不是保守，是没有数据——一次都没有。`docs_ble/answer/_facts_baseline.md` §6.4 把"血氧读数当精度证据"列为三类禁语之一，同一条也适用于技术文档。

**被问到那组 98.1%/93.8% 时**，按性质回答：那是把两个 R 值分别代进两套公式算出来的对照，用来说明公式选择本身带来的偏差量级，不是任何一次测量；我们一次真机血氧读数都没有。

**被追问"为什么做了却没数据"时**，用基线 §6.3 的句式：这块现在没有做真机标定，方案在 `docs_ble/37_real_health_roadmap.md` 阶段 3，下一步是与参考设备做对照标定。这句里同时含三件事——现在的状态、方案在哪、下一步是什么。它和"我们实现了血氧"的差别，就在于前者经得起追问。

**被追问"那为什么还要做"时**，答案落在架构而不是结果上：标定不是一个可以凭空补上的步骤，它需要一个能跑的采集与判据框架来承载。这套框架本身已经产出过一次真实价值——第一次实测的调制比 46% 被判为伪迹，进而补上了生理范围检查。判据链在假的信号上工作过，这件事有记录可查。

还有三处"代码、界面、日志"与文档口径的不一致，本章如实列在这里，不藏：页面用固定阈值把未标定的百分比分成"有效/偏低"两档（§11）；工具与 TTS 把取整后的百分比当事实念出，没有"未标定"限定（§11）；日志里 `init OK` 那一行的 `LED=12.6mA` 与同一行的回读值 `0x0c=2f`（约 9.4 mA）互相矛盾（§3）。三处的共同点是不是"写错了数"，而是**文本描述与真实行为脱节**——这正是本书记录 bug 时最看重的一类。

## 13. 做成"可用血氧"还差什么

把缺口按依赖关系排一遍，每项都说清"要什么、卡在哪"。

**第一，光学前端与波长的上限。** MAX30102 只有两个波长（红光 660 nm 与红外 880 nm），R 比值法本身就是在双波长下的近似，它无法区分"血氧低"与"灌注差、探头位置偏"这两类完全不同的原因。要跨过这个上限，需要更多波长或更好的光学前端（更大的探测面积、更稳的贴合结构）。这一项是器件级投入，不是算法能补的；在现有硬件上，任何算法改进都只能改善"信号是否干净"，不能改善"两波长能不能分开这两类原因"。

**第二，佩戴与贴合压力检测。** 目前靠调制比范围间接判断"有没有真脉搏"，这是间接证据。`docs_ble/35_auto_health_design_v2.md` §3.3 记着更硬的问题：DC 判不出佩戴，因为桌面、衣物、反光物的 DC 也很高且无搏动；该节的结论是必须加"有没有 0.5–3.5 Hz 搏动"这个第二判据，并指出这些量在**心率**驱动里已经在算（`g_hr.dc`、`ac_pp`、`HR_MAX_ACDC_PCT 5`、`HR_PK5S_MIN 3`、`HR_PK5S_MAX 20`），"零额外成本"。但血氧路径没有继承这套量，它只看自己那两个调制比。树里另有 `frameworks/system/topics/src/fitness/algo_off_body.c`（离体检测话题），`ai_agent` 侧并未引用它——这是一条现成但未接线的资源。真要做，工作量在 1 到 2 天，且需要构造"戴手上/放桌/放布/悬空"四类场景做验收，`docs_ble/37_real_health_roadmap.md` 阶段 2 给的就是这套验收标准。

**第三，与参考设备的对照标定。** 这是唯一一项"不做就永远不能说百分比"的工作。需要一台参考设备，在多档血氧水平、多种佩戴压力下同步测量，采 R 与参考值的对应点，拟合模块专属曲线。`docs_ble/37_real_health_roadmap.md` 阶段 3 给的验收线是"与指夹血氧仪对比至少 3 个点，误差 ≤ 2%，做不到就只报趋势、不报绝对值"，并点明"没有参考设备，「准确」这个词就没有意义"。该文 §4 还记了一条必须写清的限度：用已有的华为手环当参考，消费级血氧普遍 ±3~5%，只能发现粗差（比如设备报 86% 而实际 98%），**不能证明临床精度**，与手环对照不等于临床验证。工作量 2 到 3 天，前置是拿到参考设备。

**第四，连续监测。** 现在是一次测量。连续监测要常驻采集线程与长期缓冲，功耗也要重算。这一项直接撞在 §8 算过的内存现实上：内部 SRAM 静态已 95.2%（`_data_snapshot_v131.md` §2），只剩 24,968 B，堆虽在 8 MB PSRAM，但常驻高频采集意味着持续的总线与 PSRAM 访问，与"降负载换电气余量"这条本板总线策略冲突。要做必须先从内存结构与总线预算里腾空间，不是加个线程能解决。工作量估算在 2 天以上，且需要与音频那条同样吃总线的路径做共存验证。

**第五，告警链路。** 阈值在设计文档里已有：`docs_ble/34_auto_health_design.md` 记的是"血氧偏低：连续 2 次 < 90%"，理由是单次可能是手指没贴稳；`docs_ble/35_auto_health_design_v2.md` 记的是"≤89%，连续 3 次、跨度 ≥20 min"，对应华为的 90% 档。但**这些阈值当前未启用**，这是对的：它们依赖可信读数，标定之前启用，一个未标定的告警比没有告警更危险——`36_adversarial_review_and_revision.md` §2.3 已把这一点判为文档自相矛盾并明确否掉。要做，前置是第三项。

**第六，持久化。** 现在没有 `spo2_history.json`，血氧结果既不落盘也不进历史，只能读到"最近一次"。要做趋势就必须落盘，并且要照心率历史已经处理过的那套规矩办：原子写（先写 `.tmp` 再 rename）、限频（避免频繁擦写 littlefs）、时间有效性检查（RTC 未对时时不写盘，否则历史里会多一条 2036 年的假记录）。这套设施在 `infra/health_store.c` 里已经成熟，复用成本低，工作量 1 天量级。

六项里，第三项是硬前提，前两项决定上限，后三项都是标定之后才值得推进的事。顺序排错会让工作量白花：先做告警或先做连续监测，都是在没有可信数值的地基上盖楼。

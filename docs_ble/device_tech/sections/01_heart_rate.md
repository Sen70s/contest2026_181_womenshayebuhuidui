# 01 心率：从红光的直流偏置里提取每一次心跳

## 1. 本章回答什么

心率是这台设备上第一个做通的健康功能，也是所有健康功能的算法范式源头。它要回答的问题看起来简单——心跳有多快——但实际要处理的问题远不止数峰：一颗红光 LED 照在手腕上，反射回来的强度里，随心跳变化的部分只占总量的千分之一到百分之二，其余全是组织、静脉血、皮肤、环境光组成的静态偏置。要在这么大的偏置上找出周期性的微小波动，并且判断这一次找到的是真脉搏还是噪声，中间隔着一整套工程。

这一章就沿着这条链路走一遍：从器件配置开始，到采样、五个变换、峰检、RR 间期、质量判据、连续确认，最后到"这一次到底算不算测到了"以及数据怎么落盘、怎么被消费。每一步都给出公式、系数的物理含义、以及为什么取这个值。

之所以把系数解释得这么细，是因为这一类算法的难点从来不是"写出滤波代码"，而是"知道系数该取多少、以及取错了会怎样"。源代码里那些"第 N 次改"的注释，就是这些判断留下的痕迹。

---

## 2. 硬件起点：MAX30102 与它的寄存器

器件是 MAX30102，通过 I2C 挂在总线上（SCL=PA41、SDA=PA42，见 `max30102.c:3427` 的血氧初始化失败文案（心率路径同在 `:2867`））。它内部有红光 LED、红外 LED、光电二极管和 18 位 ADC。心率模式只用红光（`MODE_HR 0x02`），`max30102.c:360` 一行注释说明了这个选择：红光通道足以覆盖 PPG 的搏动提取，红外通道留给血氧。

配置心率模式要看三个寄存器。

**`REG_MODE_CONFIG`** 决定工作模式，写入 `0x02` 进入心率模式。它还有一位是 SHDN（`0x80`），把 LED 与内部时钟整个关掉——这一位在后面讲资源回收时会再出现，它是"关灯"的唯一手段。

**`REG_SPO2_CONFIG`（0x0A）** 在心率模式下实际控制的是采样参数。`0x2F` 的含义是 4096nA 量程、400Hz 采样率、411us 脉冲宽度（`max30102.c:363` 的注释把这些位逐项标了出来）。为什么选 400Hz：脉搏波的基频最高到 2.5Hz（150bpm），谐波到 3.5Hz 左右，400Hz 远超 Nyquist 需求——多出来的余量不是为了采样本身，是为了后面做 4 样本平均降噪。

**`REG_LED1_PA`（红光驱动电流）** 这一项的历史不是一次调完，而是四段：`0x24`(7.2mA) → `0x3F`(12.6mA) → 回到 `0x24` → 现值 `0x2F`(9.4mA)。最初用 `0x3F`，理由是 400Hz/411us 配置下 LED 占空比只有约 16%，`0x24` 平均电流仅 ~1.2mA，信号幅度太小。后来在真机上遇到饱和：`dc≈207659`（18 位量程上限 262143 的 79%）配合 `ac_pp=0`（峰峰值为零）。

这两个数放在一起只能得出一个结论：信号贴着量程顶被切平了，动态范围没了。需要说明证据时点：`dc≈207659 / ac_pp=0` 这条是 2026-10-12（提交 `136820e`）的记录，**不是 11-02 的观测**。11-02 日志里 `ac_pp=0` 出现 0 次，`dc` 全部落在 11742–17136 区间；能在 11-02 复现的同族指纹是 `min=7672 max=257007`（257007 是 98.0% 满量程）与首窗 `ac_pp=255068 acdc=1565.03%`。`dc` 高不是"信号强"，是"饱和"。判据不是幅度大小，而是 AC 与 DC 的比例是否还有意义——AC 为零，说明波动信息已经被削掉了。

于是降到现值 `0x2F`（9.4mA），换回动态范围。`max30102.c:365-369` 记下了这次调整。**注意这里有一处源码注释与数据手册自相矛盾**：`max30102.c:369` 的注释写"从 12.6mA 降到 6.2mA"，但 `0x2F` 按同一行引用的 Table 8 是 9.4mA，6.2mA 对应 `0x1F`（全仓从未使用过）。这条注释是 `0x24` 时期的残留，与现值不符，属已知的文档瑕疵。

这个教训可以推广：**传感器的"信号强"和"信号好"是两件事。** 幅度大而 AC 为零是饱和；幅度小但 AC/DC 比例落在生理范围才是好信号。

## 3. 采样：400Hz 到 100Hz

硬件按 400Hz 采，但进入算法的样本率是标称 100Hz（`HR_FS_NOMINAL 100.0f`，`max30102.c:514`）。中间这一步是 4 样本平均：把连续 4 个硬件样本平均成一个算法样本。`0x0A=0x2F(400Hz)` 配 `0x08=0x5F(4平均)` 就是这组配置的含义，注释里直接写成了这两个值的对应关系。

为什么降到 100Hz：拦在 3.5Hz 的带通之后，400Hz 的原始率里绝大部分是带外噪声。4 样本平均相当于一个简单的低通加降采样，把高频噪声压掉的同时把样本率降到算法能处理的范围。降到 25Hz 以下不行——`HR_FS_MIN 25.0f` 是硬下限，注释说"低于它峰值检测的时间分辨率不够"。100Hz 对应每样本 10ms 的时间分辨率，对 40–200bpm（周期 300–1500ms）的峰位定位足够。

但"标称 100Hz"不等于"实际 100Hz"，这个差别在诊断里很重要，后面 §9 会讲。

## 4. 五个变换：核心算法

这是整章的重心。从原始 ADC 值到一个滤波后的波形 `y`，中间有五个变换，每个都有明确的物理依据。

### 4.1 第一步：去直流（一阶高通 0.1Hz）

```c
if (g_hr.warm == 1) { g_hr.dc = x; }        /* 初值取当拍样本 */
g_hr.dc += (x - g_hr.dc) * (2.0f * HR_PI * HR_DC_HP_HZ / fs);
ac = x - g_hr.dc;
```

一阶高通用 `dc` 作为直流估计，然后从原始值里减掉。系数 `α = 2π·fc/fs`，`fc = 0.1Hz`，`fs = 100Hz`，于是 α ≈ 0.00628。

注释给了一个关键数字（`max30102.c:518`）：`fc=0.1Hz` 比带边 0.5Hz 低 5 倍，所以**带内增益仍然有 0.98**——这一步不会削弱我们关心的 0.5–3.5Hz 频段，只是把 DC 拿掉。

为什么必须先去 DC：真机红光 DC 在 6.8 万到 14 万量级（`max30102.c` 的注释记了这个实测范围），而脉搏引起的 AC 只有千分之一到百分之二量级。不先减掉这两个数万级的静态偏置，后面滤波器的高通部分会被巨大的直流项直接压到浮点精度边缘。

初值取当拍样本而不是 0，是为了避免"dc 从 0 起步产生大幅瞬态"。这是个细节，但少了这一句，第一个样本会带来一个巨大的假跳变。

### 4.2 第二步：带通 0.5–3.5Hz（两级一阶）

```c
g_hr.lp += (ac - g_hr.lp) * (2.0f * HR_PI * HR_BP_LP_HZ / fs);
g_hr.hp += (g_hr.lp - g_hr.hp) * (2.0f * HR_PI * HR_BP_HP_HZ / fs);
y = g_hr.lp - g_hr.hp;
```

先一阶低通（3.5Hz），再一阶高通（0.5Hz），取差值得到带通输出。

**这个带宽的依据来自生理**（`max30102.c:506-510`）：静息心率 45–150bpm 对应 0.75–2.5Hz。我们取 0.5–3.5Hz（30–210bpm），比这个范围宽一档：
- 低频端留到 0.5Hz，是为了运动/恢复期与呼吸性窦性心律不齐（HRV）的低频成分
- 高频端留到 3.5Hz，是为了覆盖运动上限

注释还说明了为什么不再放宽："又比 0.1–10 窄——后者会把运动伪影与工频谐波放进峰值检测。"这句话点明了带通过窄与过宽的两种风险：太窄会丢掉真实心率变化，太宽会放进伪影。

**关于系数的精度**：注释（`max30102.c` 相应的 α 注释）承认 `α ≈ 2π·fc/fs` 是近似式，当 `fc<<fs` 时成立；与精确值 `1-exp(-2π·fc/fs)` 差约 13%。但注释说清楚了这个误差的影响面："只影响时间常数，不移动通带位置；换来不用 `expf`。"

这是一个典型的嵌入式取舍：13% 的系数误差换掉一次浮点指数运算。可接受的理由是，它改变的是滤波器建立时间（几十毫秒量级），不改变通带形状，而建立时间我们已经用 warmup 单独处理了。

### 4.3 第三步：包络跟踪

包络是后续自适应阈值的基准。它不是一个普通的低通或均值，而是有"限速上升 + 定时衰减"两条不对称规则：

```c
float ay = fabsf(y);
if (ay > g_hr.env) {
  g_hr.env += (ay - g_hr.env) * HR_ENV_ATTACK;      /* 上升限速 25% */
} else {
  /* 衰减：半衰期 2s */
}
```

**上升限速 `HR_ENV_ATTACK 0.25`** 的作用写在注释里（`max30102.c:519`）："单拍尖峰最多把包络抬 25%"。为什么需要限速：如果包络允许瞬时跟上最大值，那么一个错位的字节、一次手指碰撞、一次运动尖峰，都会把包络瞬间拉高，进而把阈值拉高，导致接下来一大段真实脉搏都过不了阈值——算法就"瞎"了一段时间。

**衰减半衰期 `HR_ENV_HALFLIFE_MS 2000`** 的作用是让包络能在心率或幅度真的变化时跟上来。2 秒是经验值：心率从 60 变到 100 的过程中，包络需要在大约几拍的时间内完成过渡，2 秒半衰期差不多是这个量级。

两条规则合起来，包络的行为是"易涨难跌，但不会永久卡在高位"。这个不对称设计是有意的——误判涨上去的代价（漏检）比误判跌下来的代价（误检伪影）更可控。

### 4.4 第四步：启动瞬态屏蔽（第六次改）

这是留过真机证据的一处修改，也是"15s 窗口必然 timeout"那个问题的真正根因。

```c
#define HR_ENV_BLANK_SAMPLES 500    /* 复位后 5s 内包络用快衰减 */
#define HR_ENV_FAST_DECAY    0.97f   /* @100Hz 半衰期 0.23s */
```

在开机的头 500 个样本（约 5 秒）内，包络上升仍限速 25%，但**下降改用快衰减**（0.97/样本，半衰期 0.23 秒）。

`max30102.c:521`、`:526` 的注释给了完整的真机取证过程：

> "手指一开始就按住时 env 被抬到 23399，阈值 0.6×env 要 ~20s 才降到真实脉搏峰以下（nth==nmax, 一个峰都过不去）——这正是「15s 窗口必然 timeout」的根因。"

把这段话拆开看逻辑链：开机瞬间 LED 上电 + DC 建立过程产生了一个巨大的 |y| 瞬态；包络按上升限速 25% 被抬到 23399；阈值是 0.6×包络 ≈ 14039；而真实脉搏的峰值只有几百到几千量级；于是所有真峰都低于阈值，一个都检不出来；包络按 2 秒半衰期衰减，要 20 秒才降到真实峰值以下；而测量窗口只有 15 秒——必然超时。

修法就是在启动窗口内用 0.23 秒的半衰期，让瞬态在 1 秒左右被"忘掉"，阈值迅速回到真实信号幅度。屏蔽窗之后恢复 2 秒半衰期，保证正常运行时对真实变化的跟踪能力。

这个案例的方法论价值在于：**超时的表象是"时间不够"，根因是"阈值太高"，而阈值高的原因是"启动瞬态没有被处理"。** 三层原因套在一起，只看表象改窗口长度（15→30 秒）只能掩盖，不能解决。

### 4.5 第五步：峰检与自适应阈值

```c
if (g_hr.warm >= HR_WARMUP_SAMPLES &&
    g_hr.prev > g_hr.prev2 && g_hr.prev >= y && g_hr.prev > thresh)
```

峰的条件是：已过 warmup（`HR_WARMUP_SAMPLES 80`，即 0.8 秒让滤波器和 DC 建立）、前面两点的值呈"先升后降"（`prev > prev2 && prev >= y`，即局部极大）、且这一点超过阈值。

阈值是 `thresh = 0.6 × env`（`HR_PEAK_THRESH_K 0.6f`，`max30102.c:526`）。0.6 这个系数取的是"明显高于包络均值但不至于漏检"的位置：太低会被噪声穿过，太高会漏掉幅度稍小的真搏动。

峰时刻要回退一个样本：`t_peak = t - HR_SAMPLE_MS`（10ms）。因为局部极大的判定是"当前点小于上一点"，真正峰顶在上一个采样点。

**不应期 `HR_PEAK_REFRACT_MS 300`**：两个检出峰之间至少 300ms。300ms 对应 200bpm，覆盖生理上限。作用是防"一次心跳被检成两拍"。

`max30102.c:527` 注释说明这个值的选择有意比 RR 下限更松：不应期 300ms（200bpm）比 `HR_RR_MIN_MS 333`（180bpm）更宽，让"贴着不应期的双检"先被不应期挡住、再让更严的 RR 下限兜底。两层过滤各管一段，不是简单重复。

## 5. RR 间期与中位数窗口：为什么从 8 改成 12

每检出两个峰，得到一个 RR 间期（毫秒），写进环形数组 `g_hr.rr[]`。窗口长度是 `RR_HIST 12`（`max30102.c:500`）。

这个值原本是 8，2026-10-13 改成了 12。注释把改的理由写得很具体，是本章最有价值的一段工程推理：

> "窗口从 4.2s 拉到 6.3s@107bpm。理由：偶数窗口中位数取 tmp[n/2]，n=8 时是'第 4 个/共 8 个'——一个双检峰就能把中位数从 561 推到 422（106 → 142bpm 的硬悬崖）；n=12 时要 6/12 才推得动，悬崖概率显著下降。"

拆开看：中位数取 `tmp[n/2]`（0-based 索引 n/2）。n=8 时取索引 4（即第 5 个值），n=12 时取索引 6。源码 `:502` 的注释写"第 4 个/共 8 个"，这与 0-based 索引的表述不一致，属注释的序数瑕疵，不影响结论方向。窗口里的 RR 值如果大部分是 561ms（106bpm），而有一两个双检产生的 422ms，那么：
- n=8：第 4 个位置很容易被那几个短值挤到，中位数直接跳到 422 → 输出 142bpm
- n=12：要让第 6 个位置变成 422，需要至少 6 个短值，概率显著下降

这是一个"窗口长度对抗离群点"的经典权衡。窗口短则响应快、抗噪差；窗口长则稳定、响应慢。这里选了 12（4.2→6.3 秒），代价是响应变慢，收益是消除了 106→142 这种 36bpm 的硬跳变。

对一个消费级心率来说，这个取舍是对的：**用户看到 bpm 突然跳 36 个点，会怀疑设备坏了**，而慢一点跟上是可以接受的。

## 6. 双检、杂峰与"丢峰留间隔"

这一节讲一个真实存在、且有真机指纹的算法缺陷，以及修复它的判断。

### 6.1 缺陷的形态

趋势监测里偶尔会出现 bpm 偏高。现象是几个观测值：142 / 136 / 122 / 116 bpm，看起来零散。但如果按"真 RR 是 561ms（107bpm）、某个位置有一个双检峰延后 d 毫秒"这个模型去拟合，能逐位吻合（`max30102.c:1400-1415`）：

| d（ms） | 该值的实际含义 | 窗口里剩下的 RR | 输出 |
|---|---|---|---|
| 422 | 真 RR 561 与双检峰间隔 | 只有 d=422 | 142bpm |
| 441 | 同上 | 只有 441 | 136bpm |
| 492 | 同上 | 只有 492 | 122bpm |
| 517 | 同上 | 只有 517 | 116bpm |

四个观测值全部对上，这不是巧合，是同一个机制的四种表现。

### 6.2 旧代码为什么算错

关键在旧代码的处理方式："**丢间隔、留峰**"。

当检出峰与上一个峰间隔太短（`rr < HR_RR_MIN_MS`）时，旧代码只跳过 `rr[]` 的写入，**却照样把 `last_peak_ms` 推进到那个杂峰上**。于是下一个峰与杂峰之间的间隔又被算了一遍——而那个间隔也是短的。真正的长间隔（从上一个真峰到下一个真峰，约 561ms）**永远补不回来**，因为真峰已经被杂峰"顶掉"了。

窗口里剩下的全是"被切短的 RR"，中位数系统性偏短，bpm 系统性偏高。

### 6.3 修法：反过来，丢峰留间隔

现在的做法是：

```c
if (g_hr.last_peak_ms != 0 && rr < HR_RR_MIN_MS)
  {
    g_hr.reject_cnt++;      /* 只计数，不写 rr[]，也不回退/不推进 last_peak_ms */
  }
```

**不推进 `last_peak_ms`**，让它继续停在上一个真峰上。这样下一拍算间隔时，是与"上一个真峰"相减，拿回的正是那个完整的约 561ms。

代价是这一拍被合并掉、不产生 RR 值。但换来的是不再有"半拍"污染中位数。注释对这句取舍写得很直白：这是"代价是这一拍被合并掉（不产生 RR），换来的是不再有'半拍'污染中位数"。

`reject_cnt` 只统计这一类归并——"过了不应期但仍短于生理下限"的峰。真正落在不应期内（300–333ms）的双检在入口就被挡住了，走的是"整拍丢弃"，不计入这个计数。两个机制各管一段，计数也不混。

### 6.4 `HR_RR_AGREE_PCT` 从 25 收到 20 的原因

这一条与上面的修法配套。

`hr_close(a, b, pct)` 判断两个 RR 是否"接近中位数"（容差按百分比）。门限是"至少一半的 RR 落在容差内"（`rr_ok = med > 0 && (agree * 2u) >= n`）。

原本容差 25%。但注释发现了一个精确的问题（`max30102.c:535`）：

> "25% 恰好放行'双检对'：`hr_close(422,561,25)` = 24.78% < 25% 判'一致'；20% 才把它挡在门外（561 的 20% = 112ms < 139ms）。"

计算一下：|561−422| = 139，139/561 = 24.78%，刚刚低于 25%，所以被判为"一致"。而这两个值恰恰是双检的典型组合（422 是 561 被双检切短的结果）。也就是说，25% 的容差会把"明显是双检产生的一对"当成"合理的一致性"，从而放行错误的中位数。

改成 20% 后，闸值变成 561×0.2 = 112ms，而实际差 139ms > 112ms，这对被挡在门外。

**这个案例说明一件事：阈值的边界值要拿真实数据去试。** 24.78% 对 25% 这种"刚好差一点"，只看代码永远发现不了，必须有真机上的具体数值组合（422 与 561）才能暴露。

## 7. 质量门限与连续确认：什么叫"测到了"

即使峰检和 RR 都出来了，也不能直接输出。`hr_feed` 后面还有一整套门控，五个条件全过才算"这一次可信"。这一段（`max30102.c:1451-1512`）是全章最像"安全联锁"的部分。

### 7.1 五道门

```c
amp_ok   = (g_hr.env >= HR_MIN_AC_AMP);              /* 幅度够大 */
junk_ok  = !(g_hr.dc > 1.0f &&
             (g_hr.env_raw * 200.0f) > (g_hr.dc * (float)HR_MAX_ACDC_PCT));  /* AC/DC 合理 */
pk_ok    = (pk5 >= HR_PK5S_MIN && pk5 <= HR_PK5S_MAX);   /* 5s 峰数在 3~20 */
rr_ok    = (med > 0) && ((agree * 2u) >= (uint32_t)n);   /* 至少一半 RR 一致 */
range_ok = (cand >= HR_BPM_ACCEPT_MIN && cand <= HR_BPM_ACCEPT_MAX);  /* 40~200 */
```

**`amp_ok`** 排除"幅度太小，可能就是噪声"。

**`junk_ok` 这一段有一个非常精妙的判断**，值得单独讲。它的公式是"原始包络 × 200 > DC × HR_MAX_ACDC_PCT（5）"，也就是"AC/DC 是否明显超过 5%"。

但关键在于它用的是 `g_hr.env_raw`（去 DC 后、带通**前**的包络），而不是 `g_hr.env`（带通后的包络）。注释（`max30102.c:1494-1502`）解释了为什么：

> "AC/DC 合理性：用**去 DC 后（带通前）**的包络算，不用带通后的 env——白噪声/错位样本是宽带信号，0.5~3.5Hz 带通会把幅度压掉约一个量级，拿 env 判会放它过关（host 仿真：6.8 万~14 万随机跳的数据会输出 133bpm 的错值）。"

这段推理很硬。假设数据是错位的字节流——数值在 6.8 万到 14 万之间随机跳。这种信号是宽带白噪声，经过 0.5–3.5Hz 的带通后，幅度会被压掉约一个量级，看起来就"像"一个合理幅度的信号。如果拿带通后的 `env` 去做 AC/DC 检查，会被骗过去，算法还会输出 133bpm 这种看起来很正常的错值。

而带通**前**的包络保留了宽带噪声的全部能量，AC/DC 会明显超标，判定为 junk。

**这个设计的教训是：判断"信号真不真"，要用未经修饰的原始量，不能用已处理过的量。** 处理步骤本身就是为真信号设计的，它对伪信号的作用不可靠。

**`pk_ok`** 要求最近 5 秒峰数在 3–20 个。3 个对应 36bpm 下限（比 40bpm 略宽），20 个对应 240bpm 上限（比 200bpm 略宽）。这一道用"峰数"检而不是"平均 bpm"检，好处是能抓到"峰分布不均"的情况——比如漏检一段后又密集检出。

**`rr_ok`** 已经在 §6.4 讲过。

**`range_ok`** 把候选 bpm 限制在 40–200（`BPM_MIN`/`BPM_MAX`）。

### 7.2 质量分与门名

```c
g_hr.q = (amp_ok ? 40 : 0) + (junk_ok ? 15 : 0) + (pk_ok ? 25 : 0) + (rr_ok ? 20 : 0);
g_hr.gate = !amp_ok ? "amp" : !junk_ok ? "junk" : !pk_ok ? "pk" :
            !rr_ok ? "rr" : !range_ok ? "range" : "ok";
```

每个条件有分值，`q` 是加权和（满分 100）。同时 `gate` 字符串记录了**第一个失败的门**，直接打日志。这是诊断设计的一部分：出问题时不用猜是哪一环，日志直接告诉你是 amp / junk / pk / rr / range 中的哪一个。

权重分配有意义：幅度（40）和峰数（25）权重最高，因为它们是最基础的信号质量指标；AC/DC（15）和 RR 一致性（20）次之，因为它们依赖前两者。

### 7.3 连续确认

五门全过还不够，候选 bpm 必须**连续 `HR_BPM_STABLE_N` 次一致**才允许更新输出（`max30102.c:1515-1545`）。

```c
if (g_hr.last_cand != 0 && hr_close_bpm(cand, g_hr.last_cand)) {
  g_hr.stable_cnt++;
} else {
  g_hr.stable_cnt = 1;
}
g_hr.last_cand = cand;
if (g_hr.stable_cnt >= HR_BPM_STABLE_N) { ... 输出 ... }
```

注释说这样做的价值："单次异常峰（哪怕混进中位数）只会让计数回到 1，推不动 bpm。"

这是最后一道保险：即使前面五道门都被一个足够像真信号的伪影骗过，只要它不连续出现，就推不动输出。

### 7.4 跳变保护

通过连续确认之后还有一层：如果新候选与当前 bpm 差得远，需要"持续偏离"的独立确认（另一组 `jump_cnt`），否则保持上次值。

```c
if (!g_hr.have_bpm || hr_close_bpm(cand, g_hr.last_bpm)) {
  *bpm_out = hr_slew_bpm(cand);        /* 首次锁定或缓慢跟踪 */
} else {
  /* 与当前 bpm 差得远：需要独立确认 */
  if (g_hr.last_jump_cand != 0 && hr_close_bpm(cand, g_hr.last_jump_cand)) {
    g_hr.jump_cnt++;
  }
  ...
  if (g_hr.jump_cnt >= HR_BPM_STABLE_N) { *bpm_out = hr_slew_bpm(cand); }
}
```

注释把意图说得很清楚："这就是'分钟级稳定、不因单次异常峰跳变'的落点；心率真实变化会在几次心跳内被连续确认，然后一次性跟上。"

另外有 `hr_slew_bpm` 对每次更新的变化量做限速。首次锁定不设限速（否则冷启动会很慢），之后每次最多走 `HR_BPM_SLEW` 个 bpm。

### 7.5 "刻意不做"清单

`max30102.c:131-150` 有一段诚实到少见的记录，列出**刻意没有做**的东西：

> "①自适应不应期（clamp(0.5×RR_prev, 300, 600) 在 >=100bpm 时是空操作）……"

意思是"自适应不应期"这个常见做法在心率 ≥100bpm 时算出来的值都落在 300–600 区间之外，等于没生效——所以不做，不做无用复杂度。

这类记录的价值高于"我们做了什么"：它说明团队知道有哪些常见做法，并且判断过、决定不做，而不是不知道。

## 8. "测到了"的判据：`hr_measure_last_ok()` 的诚实性红线

这一节讲算法之外的一层：**上层怎么知道这一轮到底有没有测到。**

算法会持续输出 bpm，但"输出过 bpm"不等于"这一轮测到了"。困难在于失败轮：`hr_measure_last_bpm()` 可能残留最后一次成功 copy 到的非零值。如果上层只看 bpm，就会把失败轮当成功轮，进而显示一个过期数字、甚至触发告警。

所以有了 `hr_measure_last_ok()`（`hr_measure.h` 的接口注释写得很明确）：

```
 * 给后台守护用：失败轮（信号弱/超时）里 hr_measure_last_bpm() 可能
 * 残留最后一次 copy 到的非零值，只看 bpm 会把失败轮当成功轮。
 * 读结果的一方应**先看本函数、再看数值** —— bpm==0 / last_ok==false
 * 都绝不告警、绝不显示 0（诚实性红线）。
```

接口注释里"诚实性红线"这个词用得很重，因为它确实是红线：**测不到就不显示，绝不显示 0，绝不显示上次的值。** 显示 0 会被用户理解为"心率是 0"（医学上意味着心脏停跳），显示上次值会让用户以为设备在工作，两者都比"测不到"更糟。

这条约束贯穿整个健康模块。心率历史、每日摘要、告警链路都遵循同一个原则：缺数据就省略，不补、不猜、不显示 0。

## 9. 诊断字段怎么读

`hr_algo_diag()`（`max30102.c:1603` 起）每 `HR_STAT_MS 2000` 毫秒打一行诊断。这一行的每个字段都对应一个可排查的方向，`max30102.c:1571-1595` 的注释逐项说明了：

```
fs=  本窗口"入算法样本数/窗口时长"
fed= 累计入算法样本数
dc=  去 DC 后的直流（原始量级）
ac_pp/ac_rms= 去 DC 后的峰峰值/均方根
bp_pp/bp_rms= 带通后的峰峰值/均方根
acdc= ac_pp/dc 的百分比
```

**`fs`（有效采样率）** 是最先要看的。注释说："fs 明显低于 25Hz 说明样本流是'陈旧尾/重复样本'堆出来的（samples 涨得快也没用）。"这句话点出一个典型陷阱：样本数在涨，但涨的是重复样本，实际有效信息没有增加。只看 `fed` 会以为采样正常，实际 `fs` 已经崩了。

诊断行里出现过偏离标称值的 `fs`（例如高于 100Hz 的窗口），这类记录正是排查样本流问题的第一手材料。

**`dc`（直流）** 判饱和。§2 讲的红光电流从 12.6mA 降到 6.2mA，就是靠 `dc≈207659` 这个值判出来的。

**`ac_pp`/`ac_rms`（去 DC 后的峰峰/均方根）与 `bp_pp`/`bp_rms`（带通后）的对比**是最有诊断价值的一组。注释（`max30102.c:1570-1580`）：

> "生理 PPG 的 AC/DC 只有 0.1%~2%，几十个百分点说明拿到的根本不是脉搏波（字节错位/陈旧样本/运动）——这时**不该**去调阈值，该查读法/电极/接触。"

这句话给了一个明确的排查方向分流：如果 AC/DC 明显超出 0.1%–2%，问题不在算法参数（调阈值没用），而在数据本身（读法、电极、接触）。这个分流能省掉大量"改参数试一下"的徒劳。

**`acdc`** 直接把 `ac_pp/dc` 算成百分比，是最直观的判据。

真机日志里还有一行 `[hr_sensor] algo fs=117.4Hz fed=241 rst=0 ovfs=0 dc=12066 ac_pp=170 ac_rms=37 bp_pp=110 bp_rms=22`——`dc=12066` 说明这一轮没饱和（远低于 207659），`ac_pp=170` 相对 `dc=12066` 是 1.4%，落在生理范围内。这行日志本身就是一个"信号正常"的判据实例。

## 10. 异常与自愈

传感器会出各种异常，恢复机制是分层的。

**FIFO 溢出**：`HR_OVF_STUCK_ROUNDS 20` 在第四次改之后**不再是控制流、也不触发恢复**，只用于在连续 20 轮 `OVF != 0` 时打**一条**提示（只打一次）。注释明确写着"现在只记账"，并指出真机 0x05 恒非 0 是旧读法把写指针拉回起点造成的假阳性；真正的判据要看 stat 行的 `fresh=`/`rdup=`（读侧）与 algo 行的 `dup=`/`d1=`（信号侧）。这个变化是第四次改的核心：旧代码每 50ms 清指针，导致 `dup` 高达 97~100%。

**样本卡死**：`HR_STALE_CLEAR_ROUNDS 40` / `HR_STALE_CLEAR_MIN_MS 10000`——样本流停滞超过 10 秒且满 40 轮，清空重来。

**无中断**：`HR_NOINT_STREAK 20` 的语义与"判器件无响应"相反——连续 20 轮 `INT_STATUS` 都读到 0 时，它认为"PPG_RDY 位定义/使能位"的假设在本板不成立，于是**自动改成每轮盲读**，宁可多花 3×N 字节总线时间也不让采样饿死。自愈方式是哪一轮重新读到非 0 状态就立刻回到门控。**它不触发 `hr_recover`。**

**恢复函数** `hr_recover()`（`:2086`）：重新复位器件、重写配置、清 FIFO、重置滤波器与算法状态。`HR_RECOVER_FAILS 20` / `HR_RECOVER_MIN_MS 2000` 限制恢复的频率，避免在真故障时反复重启制造更多问题。

这几组常量的共同设计思路：**用"连续 N 次异常"而不是"单次异常"作为触发条件。** 单次 FIFO 溢出可能只是采样稍慢，单次无中断可能只是轮询时序差异；只有连续 N 次才说明真的卡住了。这个模式在嵌入式里很常见，因为单点异常的概率远高于持续故障。

还有 `HR_FIFO_MIN_SAMPLES 5`、`HR_SKIP_SAMPLE_AFTER_CLEAR`、`HR_RING 512`（原始样本环，约 5 秒 @100Hz）等，都是为"清空后不要立刻用旧状态"设计的。

## 11. 落盘与 RTC 陷阱

心率结果的持久化在 `hr_measure.c`，环形容量 `HR_MEASURE_HISTORY_CAP 288`（定义在 `health/hr_measure.h:113`，同一头文件 `:117` 还有 `HR_MEASURE_HISTORY_JSON_MAX 12288` 限制 JSON 大小）。

288 这个数的来源可以推算：10 分钟一轮静默测量 × 288 = 48 小时，即两天的历史。这个容量对"看趋势"够用，对"长期健康档案"不够——但受限于内存不能更大：内部 SRAM 静态占用已达 **94.7%（基线 §5）**，已接近上限。真正危险的不是这个总量，是开机早期堆余量（见 04 章）。再放大这个 288 条的数组会直接压缩那一块。

**原子写**：先写 `<name>.json.tmp`，再 rename 成 `<name>.json`（`infra/health_store.c` 的 `path_of()` 实现了 tmp 后缀）。这个模式的必要性在于：littlefs 上如果直接覆盖写，写到一半断电会留下一个半截 JSON，下次解析失败，历史全丢。tmp+rename 保证了"要么旧版完整，要么新版完整"，不存在中间态。

**RTC 陷阱**：这是最容易被忽略的一类问题。真机见过开机瞬间 RTC 读到 2036 年——因为 RTC 还没对时，读出来的是未初始化值或残余值。如果不拦截，历史里就会多一条 2036 年的假记录，而这会让所有基于时间的历史查询（7 天历史、当日汇总）失效。

处理方式是设有效区间：年份在 2020–2027 之外时**不写盘**。启动日志里能看到这类记录被丢弃。`pedometer.c` 也用了同一套判据（`DATE_VALID_UNTIL`）。

这个细节的意义：**"能写"和"该写"是两件事。** 数据落盘的价值在于它以后能被正确检索，一条时间戳错乱的数据会污染整个历史，不如不写。

## 12. 两条测量路径与告警链路

心率的采集有两条路径，共用同一套算法与判据：

**用户按钮路径** `hr_measure_start()`：用户点"测心率"，起 worker 线程，会上"测量中"进度、结果上屏、进 TTS 播报。失败也会提示。

**后台静默路径** `hr_measure_start_silent()`：由 `hr_watch` 每 `HR_WATCH_INTERVAL_S 600` 秒（10 分钟）触发一轮，**跳过全部 UI 与语音**——不上进度、不上屏、不进 TTS、失败也不弹提示。`hr_measure.h` 的注释解释了为什么："后台周期测量不能打扰用户。"

两条路径**共享同一个 `busy` 标志**（单飞语义）：任一在跑，另一个调起就返回 `-EBUSY`。这个设计避免用户点按钮时正好撞上后台静默测量——两颗流程抢同一颗芯片。

**告警链路**：`hr_watch` 在静默测量成功后，若 `bpm >= BPM_HIGH`（120）就通过 `pet_care` 触发主动关怀。11-02 真机日志里能看到这条链路完整走通：`[hr_measure] success: bpm=167 (silent)` → `[hr_watch] high bpm=167, reporting` → `[pet_care] hr alert 167 bpm`（16:24:42–44）。这条链路上还叠了冷却与免打扰窗口：同一次高心率不会反复告警，夜间不打扰。

`hr_watch.h` 里 `BPM_HIGH 120` 这个阈值的选择依据是一个保守判断：正常静息心率 60–100，120 是一个明显偏高的位置，能减少误报；同时又不至于高到漏掉真实异常。

**这里有一个必须主动讲的诚实点**：告警数据源是真的，但它不是模拟的。旧的 `hr_monitor.c` 是一个模拟随机游走的实现，会自己弹"你心率有点高"。这个模块已经于 2026-10-22 从 1Hz 调度摘除，代码注释写着"不报比报假的强"（`src/ui/pet_care.c:509`）。

## 13. 被删掉的模拟心率：一个反向的功能

这一节值得单列，因为它讲的是一个"删功能"的决定，而这个决定的正确性高于多数"加功能"。

`hr_monitor.c`（现 156 行）的历史形态是模拟数据源：用随机游走生成 bpm 值，喂给上层，让心率告警、心率页面在早期开发阶段有数据可看。这在开发期是合理的——没有真实传感器时，你需要假数据来验证 UI 和告警逻辑。

但它留下的风险是致命的：**假数据一旦留在产品里，用户看到的"心率"就是编的，而基于它的告警会误导人。** 对健康类功能，这已经不是质量问题，是伦理问题。

2026-10-22 的处理是从 1Hz 调度里摘除，保留文件但不运行。代码注释"不报比报假的强"（`src/ui/pet_care.c:509`）是这次决定的书面依据。

现在的告警数据源是 `hr_watch.c` 的真实静默测量，判据是"成功才记录、测不到不显示 0、`last_ok=false` 绝不告警"。

这个决定的对外价值：它可以在答辩里作为正面案例讲——我们主动删掉了会造假的功能。而多数团队会把假数据留在演示里，因为"看起来功能更全"。

## 14. 边界：真实出数，但不宣称准确

心率这一章的最后必须讲边界，而且要比血氧那一章更细致，因为它有真实数据，边界就更难划。

**可以说的：** 心率是真实的传感器测量，MAX30102 红光 PPG；单次测量窗口上限 30 秒；后台每 10 分钟静默测量一轮；告警阈值 120bpm，数据源是真实测量而非模拟；历史 288 条环形落盘、重启不清零；算法有完整的五门质量判据与连续确认。

**不能说的：** "心率准确"、"误差 ±5bpm"、"医疗级"、"可以诊断心律异常"。

为什么"真实出数"和"准确"是两个不同的话，值得讲清楚。**11-02 真机读数 167bpm**（`[16:24:42] [hr_measure] success: bpm=167 (silent)`，`.v3_work/logs/serial_ts.log` 15:49–20:10 观测、v114 系列）；**历史观测另有 142 与 171**（更早时点，出处见基线 §5）。这些读数跨不同佩戴状态，分布本身恰好说明「真实出数但不保证一致」，这些值都是真实测出来的，但**"真实测出来"不等于"和真实心率一致"**。要证明一致性，必须做对照验收：同时用医用设备或胸带心率计测量，比较两者的差值分布，确认偏差在可接受范围内。这件事没做。

所以口径是"真实出数，看趋势，精度未做对照验收"。这个表述比"心率准确"弱，但它是可辩护的——如果评委追问"你怎么证明准确"，前者能回答"我们没证明，所以不宣称"，后者会被当场戳穿。

## 16. 这一章真正的结论

心率是本设备上唯一一条"传感器 → 算法 → 判据 → 持久化 → 告警"全链路都跑通过、且有真实数据的功能。它之所以值得写这么长，不在于算法复杂，而在于它浓缩了几类反复出现的判断模式：

**处理顺序有物理依据。** 去 DC 必须在带通之前，因为 DC 比 AC 大三个数量级；带通必须在包络之前，因为包络要在"清洁"的波形上算；包络必须在阈值之前，因为阈值要随信号强度自适应。每一步的先后不是随意排的，是被数据量级和物理意义决定的。

**判据要分层且各管一段。** 不应期（300ms）挡双检，RR 下限（333ms）挡"过了不应期但仍太短"的归并，五门质量判据挡"节律合理但信号是假的"，连续确认挡"骗过了前面所有门的一次性伪影"。四层不是重复，每层的失败模式不同。

**判断信号真伪要用未经修饰的量。** `junk_ok` 用带通前的包络而不是带通后的，因为带通会白噪声压掉一个量级，让伪信号看起来合理。这个原则可以推广到所有"用处理后数据反推输入质量"的场合。

**阈值的边界值必须拿真实数据试。** 25% 容差对 24.78% 这种"差一点"，只看代码永远发现不了。真机上的 422 与 561 这对数值，才是发现问题的钥匙。

**诚实性红线在"测不到"这一侧。** 显示 0 会被理解成心脏停跳，显示上次值会让用户以为设备在工作；两者都比"测不到"更糟。所以 `last_ok` 必须与数值分开看，缺数据就不显示。

心率这一章能把"真实但不宣称准确"讲得站得住，是因为上面每一条都有代码位置与真机证据支撑。而血氧那一章之所以只能讲到"算法骨架"，缺的正是最后一步——用外部参考设备跨过标定那道门槛。

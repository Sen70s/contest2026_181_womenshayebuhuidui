## 0. 这本文档要解决什么问题

市面上讲智能穿戴的资料，大多停在"它有心率、有步数、有睡眠"这一层。可真要复现或者审阅一个实现，真正难回答的不是"有没有"，而是：心率那个数字是怎么从一个红外接收器的电压值变出来的？中间每一级的系数凭什么取这个值？哪一步失败会怎样？凭什么说这次"测到了"而不是噪声？

这本文档就是回答这类问题的。它不写产品介绍，不写功能清单——每一章都沿着**一条数据**走完整程：从物理世界的信号开始，经过采样、滤波、判据、语义推断，最后落盘、被上层消费、被展示或被播报。四个人类可读的功能（心率、血氧、运动、休息）各占一章，再加一章讲显示、音频、网络、内存、功耗这些系统级数据链——它们虽然不是"健康数据"，但同样遵循"测量 → 判读 → 结论"的模式，同样会骗人。

### 0.1 三条贯穿全书的写作纪律

**第一条：每个结论后面必须有证据位置。** 证据分三类，全书统一：代码（`文件:函数:N行`）、文档（`docs_ble/NN` § 章节）、真机日志（串口关键字）。凡是说不清证据的，一律写"未确认"，绝不补猜测。

**第二条：数字只有一个来源。** 全书用 `_data_snapshot_v131.md` 的口径，内存统一按基线 §5 的 94.7%。这与 2026-11-02 定稿的答辩材料不同——答辩材料用的是 v114b14 口径（106 基线 / 94.7% / 7.15MB），两套都各自自洽，但**不可混引**。原因很实际：答辩材料已经过外部评审定稿，不应因本文档而返工；而技术文档必须对得起"当前固件"这四个字。凡本文档出现与答辩材料不同的数字，都是因为固件在两天里又往前走了 25 个基线。

**第三条：边界比能力更值得写。** 血氧这一章是最典型的例子：算法代码是完整的，UI 入口是有的，工具也注册了——但**没有任何一次真机 SpO2 读数**，也没有做标定。所以那一章的正确写法是把算法讲透、同时明确"不宣称可用"。把边界讲清楚，比多吹一个功能更有价值，因为前者经得起追问。

## 1. 全设备数据管线总图

### 1.1 三层数据源

这台设备上的所有数据，起点只有三类物理器件加两类软件源。

**第一类是光学传感器 MAX30102。** 它通过 I2C 挂在总线上，内部是一颗红光 LED、一颗红外 LED 和一个光电二极管。LED 打光，二极管接收反射光，反射强度随血液容积变化而波动，于是得到一个叫 PPG（光电容积脉搏波）的时域信号。心率只用红光通道（`MODE_HR 0x02`），血氧必须红光加红外双通道（`MODE_SPO2 0x03`）。这颗芯片是心率与血氧的共同源头，也是它们互相干扰的根源——见 §1.4。

**第二类是惯性传感器 IMU。** MPU6500/9250 兼容芯片（`WHO_AM_I=0x70`），I2C 50kHz，±4g 量程，通过 `/dev/mpu0` 暴露。轴向加速度是步数与休息判定的唯一输入。

**第三类是系统自身产生的时序数据**：显示刷新（`lcd_flush` 计数）、音频帧（PCM 采样）、网络报文（PAN 帧）、内存占用（`.bss`/`.data`）。这些不是"传感器数据"，但同样需要"测量 + 判读"，而且它们是 01–03 那些健康数据能否被用户感知的前提。

### 1.2 一条数据要穿过四层

不论起点是哪一类，数据在设备内部都要穿过同样四层，每层都可能丢、可能错、可能被误读：

**驱动层**负责把器件时序变成可用的样本流。这一层最容易出"看起来在工作、实际全错"的故障——麦克风那个案例就是驱动漏调一个函数（`HAL_TURN_ON_PLL`），ADC 输出全 0 或全 FF，但代码逻辑完全正确。这类故障的共同特征是：上层算法收到的是"格式合法但物理无意义"的数据。

**算法层**负责从样本流里提取语义。心率要从 PPG 里数峰，血氧要从两个通道算比值，步数要从加速度里识别步态，休息要从静止时长推断状态。这一层的每一步都是判据加阈值，而阈值取多少、为什么取这个值，是本文档最关心的内容。

**存储层**负责把结论持久化。统一由 `packages/ai_agent/src/infra/health_store.c` 管理，落在 `/data/ai_agent/health/<name>.json`，实现方式是"先写 `.tmp` 再 rename"的原子写。这一层最隐蔽的坑是时间：RTC 未对时的时候设备可能读到 2036 年，若不拦截，历史里就会多一条 2036 年的假记录。

**消费层**负责把结论变成用户能感知的东西——页面上的数字、TTS 播报的一句话、每日摘要里的一句问候、LLM 工具调用返回的 JSON。这一层决定了前面三层的努力是否有意义，也决定了错误的传播路径。

### 1.3 落到磁盘的四份健康文件

所有健康数据最终收敛成四个 JSON，都在 `/data/ai_agent/health/` 下：

| 文件 | 内容 | 生产者 | 消费者 |
|---|---|---|---|
| `steps.json` | `date` / `steps` / `history`（7 天） | `health/pedometer.c` | 运动页、`get_steps`、每日摘要 |
| `hr_history.json` | 288 条环形（时间戳 + bpm） | `health/hr_measure.c` | 心率页、`get_heartrate_history` |
| `rest.json` | `last_night` + `sessions`（最多 7 条） | `health/rest_track.c` | 睡眠页、`get_rest`、每日摘要 |
| `summary.json` | 最近一次每日摘要的 `date` | `ui/health_summary.c` | 防重复生成 |

四份文件共同的写入纪律是：限频（步数 60 秒才写一次，避免频繁擦写 littlefs）、原子写（tmp + rename）、时间有效性检查（不对时就只读不写）。这三条不是优化，是防止数据被自身的写入行为破坏——这是嵌入式持久化最常见的翻车点。

### 1.4 一个必须提前讲清的架构事实：心率与血氧共用一颗芯片

这是全书最容易引起误解、也最容易出真 bug 的地方，必须在总纲里说清楚。

心率与血氧不是两颗传感器，是**同一颗 MAX30102 的两种工作模式**。心率模式只开红光（`MODE_HR 0x02`），血氧模式必须同开红光与红外（`MODE_SPO2 0x03`）。两种模式的寄存器配置不同：`SPO2_CONFIG`、两个 LED 的驱动电流、FIFO 深度都不一样。

后果是：如果血氧测量进行到一半，用户又点了"测心率"，就会走进一个危险的交叉状态——`inited` 标志已经为真，于是跳过重新初始化，在 `MODE_SPO2` 的寄存器状态下走心率采集路径。读到的数据在格式上合法，在物理上无意义。这个 bug 是在 2026-10-19 的对抗审查里确认的，修复方式是把所有权锁放在驱动层（`sensor_claim`/`sensor_release`，枚举 `SENSOR_OWNER_NONE/HR/SPO2`），而不是放在应用层的按钮回调里——因为在应用层拿不到驱动内部状态。

这个设计选择值得记住：**互斥留在最靠近资源的那一层**。放在应用层只是"两个按钮互斥"，放在驱动层才是"两个物理使用者互斥"，后者才能覆盖所有入口（按钮、工具调用、后台守护、串口命令）。

### 1.5 五条系统级链路与它们的共同瓶颈

若把视角从健康数据拉远到整机，会发现 01–03 的所有内容最后都被五条链路约束着：

**显示**：LVGL 渲染 → 脏矩形 → QADSPI 推送 → 面板 GRAM。没有 GPU，全部软件绘制。这条链路决定"用户能不能看到"。
**音频**：云端 PCM → 环形缓冲 → APB → DMA → 喇叭。这条链路决定"用户能不能听到"，也是整机崩溃的最集中来源（DRAINING 状态陷阱、mq 队列睡死、TCB 复用断言）。
**网络**：bt-pan 选路 → TLS → 报文。这条链路决定"数据能不能进出"，且有一个硬的物理上限（每帧 487 字节 × 约 31 毫秒）。
**内存**：内部 SRAM 静态 94.5%，外部 PSRAM 8MB 基本空着。这条链路决定"能不能再加功能"。
**功耗**：电池未装机、未实测，只能给估算。这条链路决定"能给什么续航承诺"。

这五条的共同瓶颈只有三个：**线程**（LVGL 是 `LV_OS_NONE`，绝不能在渲染线程上阻塞）、**内存时序**（PSRAM 堆要等 `up_initialize` 之后才加入，而内核 idle 组初始化在它之前）、**单条蓝牙链路**（所有出网数据都挤在 487 字节一帧的节拍上）。

### 1.6 总图：以一次语音问答为例

把上面所有抽象落到一次具体交互，能看到数据如何穿过全部四层五链路：

用户说一句话 → 麦克风（ADC +30dB 增益）→ VAD 静音检测只保留语音段 → 降采样到 8kHz → 经 bt-pan 上传云端 ASR → 云端识别成文字 → agent loop 把工具清单（47 个注册工具）与上下文一起发给云端 LLM → LLM 返回工具调用或直接回答 → 若需工具则本机执行并把结果回填 → LLM 组织成 1–2 句话 → 云端 TTS 合成 PCM → 经 bt-pan 下载到环形缓冲 → 音频驱动分 APB 交给 DMA → 喇叭播出，同时屏幕显示全文。

这条链路里每一跳都有明确的字节量与耗时，也都能被单独测量。但也正因为每一跳都串在同一条蓝牙链路上，其中任何一处的字节量变化都会改变整轮耗时——这就是为什么本机的优化方向不是"等网络变好"，而是"把要传的东西变小"。

更完整的量化模型在 04 章 §4。

## 3. 这本书里反复出现的五种"骗"

技术文档如果只讲"怎么做对了"，价值有限。更有价值的是讲清"怎么被骗过"——因为下一个实现者大概率会踩同样的坑。全书出现的骗局可以归成五类，每类都至少有一个真实案例。

**第一类：编译通过不等于生效。** 代码写了、编译过了、链接过了，功能依然不工作。典型案例是实时语音采集"从来没工作过"——录音函数全是 weak 桩，真实现根本没编进固件，但离线路径能出结果，把问题盖住了。判据是符号表：`nm` 看到一堆 `W` 就是假实现。

**第二类：代码正确不等于链路正确。** 麦克风那个案例，驱动代码逻辑完全正确，唯独少了一个 `HAL_TURN_ON_PLL` 调用。四轮代码审查都审不出来，因为审查只能审"有"的东西，审不出"缺"的东西。破解方法是对着厂商参考序列做差集。

**第三类：现象相同不等于根因相同。** TTS"播报不完整"看起来是尾部丢失，于是加尾部等待、加延迟，做了好几版都没解决。后来发现是第 45 字左右整齐截断——问题根本不在播放层，在文本生成层。区分"尾部丢失"和"长度截断"，是那一轮排查的全部价值。

**第四类：日志会说谎。** 第一版自动判 PASS 的稳定性脚本，把上一轮还没结束的旧日志混进了本轮，于是判出一个很差的成绩，其实设备是好的。结论必须以原始串口日志按启动段重新解析为准，脚本结果只作参考。

**第五类：数据合法不等于物理有意义。** 这是最危险的一类。血氧测量中途切心率那个 bug，读到的 FIFO 数据格式完全合法，但对应的是错误的 LED 配置。防御手段只有一个——把互斥放在最靠近物理资源的那一层。

这五类骗构成了全书的方法论背景。每一章讲"我们怎么修的"时，实际都在演示如何识破其中某一类。

## 4. 怎么读这本文档

**如果要复现某种算法**：跳到对应章节的核心算法节。01 的"五个变换"、02 的"R 比值与中位数"、03 的"带通与双判据"，都给了公式、系数与这一段代码的行号。

**如果要审阅工程判断**：读每章的"刻意不做"与"边界"两节。工程能力的体现往往不在做了什么，而在明确不做什么以及为什么。

**如果要排查故障**：先读对应章节的"诊断字段读法"和"异常与自愈"。01 的 `fs/fed/rst/ovfs/dc/ac_pp/ac_rms/bp_pp/bp_rms`、04 的 `lcd_flush`/`alive`/`[stall]` 都是为此设计的。

**如果要评估对外能不能讲**：读每章最后一节"边界"，以及 02 章第 1 节的诚实边界声明。
